从一笔 GetTID 读懂 AF_MCTP、libmctp 与 libpldm

源码分析

上次查 Target 的 TID，Host 打印了六个字节。

开头和结尾都是 01。第一个表示这条 MCTP 消息承载 PLDM，最后一个才是设备返回的 TID。还有一个容易漏掉的细节：这行是原 requester 把类型和正文放在一起打印的。在我们部署的内核上，应用实际从 socket 数据区读到的是后面五个字节。之前 Host 就在这个边界多放了一个类型字节，链路能通，Target 看到的命令却错了一位。实板 GetTID 记录 · 当时的定位过程

一张图看清两端各跑什么

Host 和 Target 共同遵守 MCTP 的包格式，各自有一套收发实现。Host 用 Linux 内核的 MCTP 栈，应用通过 AF_MCTP 访问它。我们交付的裸机端点把 libmctp 编进固件组件，应用通过回调接收消息。两头都用到 libpldm，因为两头都要读写 PLDM 字段。

Host 从哪里得到去往 EID 9 的路

这台 Host 运行 6.6.36-slim-mctp。CONFIG_MCTP=y 把通用消息栈编进内核。传输侧由 mctp-i3c.ko、I3C core 和 SVC 主控驱动配合；I3C binding 的来源是 Linux v6.8，回移时适配了当前板的读长度和包长约束。看到这几个模块就能解释 MCTP 怎么上总线。PLDM Base 命令的实现还得去用户态程序和对端固件里找。Linux 的 MCTP 栈结构 · v6.8 I3C binding 源码

mctp 工具通过 netlink 查看或配置内核的网络对象。下面四个命令读的是本机状态，都不会向 Target 发一条 GetTID。

命令 这次记录里能看到什么 内核发送时怎样用它
mctp link show mctpi3c0 在 network 1，UP，MTU 68 选择承载接口及包长
mctp address show 本地 EID 8 形成 MCTP 源地址

mctp neigh show EID 9 对应一个六字节 I3C PID binding 按 PID 找到枚举后的设备，从设备描述符取得当前动态地址

这次 I3C 枚举后动态地址是 0x44。Host 上的 network 1 是本地的 EID 地址空间标识，不会作为一个额外字节发上 I3C。路由和邻居由脚本按固定拓扑配置，这套部署没有常驻的 mctpd 去动态发现、分配 EID，也没有 pldmd 和 D-Bus 服务来代为完成查询。当时的接口、路由及邻居表

第一段代码：应用交给 socket 的三个字节

取实例号 3，GetTID 的请求正文恰好只有三个字节。下面是独立写的发送示例。调用方持有已经打开的 socket(AF_MCTP, SOCK_DGRAM, 0)，同一描述符还要用来等待响应。

0x83 是 Request 位加实例号 3，0x00 是 PLDM Base，0x02 是 Base 里的 GetTID。另一个命名空间里的 0x01 放在 smctp_type。指定 MCTP_TAG_OWNER 后，内核为这笔请求分配可用的消息 Tag，保留响应回到这个 socket 所需的关联。这个 3 位 MCTP Tag 和 PLDM 头里的 5 位 Instance ID 可以有不同的值。函数返回 3，只表示内核接受了三字节正文；业务是否成功要等回包。

这里值得直接看 net/mctp/af_mctp.c：mctp_sendmsg() 先查 network/EID 路由，在 skb 中追加一字节 smctp_type，再复制用户数据。mctp_recvmsg() 则取出该类型，从偏移 1 开始复制正文，并在返回的 sockaddr_mctp 中填写类型、源 EID 和 Tag。随这棵 6.6 内核附带的文档示例还写着让应用自己把 type 放进发送缓冲区；移植到这台板时，应以这对函数和实际请求结果为准。Linux v6.6 的发送与接收实现 · 同版本文档示例

从一个数据报到一次 I3C 写

  1. mctp_local_output() 选择出口的本地 EID，处理 Tag，填好源、目的地址。需要切片时，mctp_do_fragment_route() 给各片写 SOM、EOM 和循环递增的两位序号。同一消息的各片沿用 Tag，类型字节只出现在首片。
  2. mctp_route_output() 使用邻居表，把包送进 netdev。binding 的 mctp_i3c_start_xmit() 交给发送线程，再由 mctp_i3c_xmit() 找到 I3C 设备，计算写方向 PEC，发起 Private Write。
  3. 返回时，Target 准备好响应，使用带 0xAE 的 IBI 通知 Host。Host 的 mctp_i3c_ibi_handler() 触发 mctp_i3c_read() 发起 Private Read。IBI 只通知“可以来读”，真正的响应在随后的读事务里。
  4. 本板的读请求上限可以是 69 B，这次 GetTID 实际只返回 11 B。驱动按 actual_len 找最后一个字节验证 PEC，移除它，再调用 netif_rx() 上送。内核匹配 Tag 和地址；分片消息需由 mctp_route_input()、mctp_frag_queue() 收齐，应用才收到完整数据报。Linux v6.6 的路由、分片与接收 · I3C 绑定与本板适配

Target 为什么要有 libmctp

裸机上没有进程，也没有等在 recvmsg() 上的用户线程。libmctp 给平台留了两头接口：往下注册一个 binding，把包交给硬件；往上注册一个消息回调，把完整请求交给业务。初始化时，交付组件先 mctp_init() 创建实例，设置时钟和消息大小上限，以本地 EID 注册 binding，再用 mctp_set_rx_all() 安装 on_message()。消息类型 0x00 的 MCTP Control 请求由该版本的 Control 逻辑处理；类型 0x01 才进这里的 PLDM 分发。固定版本 libmctp 的 core · Target 交付组件源码

在接收方向，平台把 Private Write 的有效长度和动态地址交给 chip_endpoint_rx()。它按写方向验证 PEC，去掉末尾校验字节，把剩下的 MCTP 包交给 mctp_bus_rx()。假如收到的是首片且 EOM 尚未置位，PLDM handler 还拿不到可执行的命令。等消息完整后，回调才看到连续的 [类型][PLDM 头][命令数据]。同一笔 GetTID，此处要跳过第一个字节，Host 的 AF_MCTP 数据区却从 PLDM 头开始。

下面把回调中一条成功分支单独写出来。调用前已经确认这是发往本端的 Base/GetTID 请求、请求有 Tag Owner、头合法且命令数据长度为零；local_tid 来自端点状态。

回包目的 EID 取自来包源地址，Tag 沿用，Owner 清零，PLDM Instance ID 原样返回。库可以立刻把生成的 packet 交给 binding，主机却可能过一会儿才来读。因此 binding_tx() 复制包到软件队列；chip_endpoint_tx_peek() 再按读方向加 PEC，平台装好稳定的硬件发送缓冲后才发 IBI。读事务正常结束且实际长度吻合，chip_endpoint_tx_complete() 才把队头移走。这是交付组件和板级代码的接口约定。实板成功回包印证了外部行为，最新固件内的中断与主循环具体怎样交接，尚缺匹配的固件版本材料。交付接口与完成条件

libpldm 管哪一段，pldmtool 又多做了什么

只给 libpldm 一个缓冲区，它就能编码 GetTID 请求，或者解出响应中的 TID。函数没有 network、EID 或 I3C 地址参数。设备端调用 encode_get_tid_resp() 时也要传入 TID，它的值由应用维护。

以端点采用的 v0.13.0 为例，核心数据结构是三字节的 pldm_msg_hdr 和后面的命令 payload。公共头处理函数负责 Request/Response、Instance ID、PLDM Type 和 Command；src/dsp/base.c 等按协议类型分组的 codec 再读写各命令专有字段。同一个成功响应，在 Base/GetTID 里第二个 payload 字节是 TID，换一个 Command 就得换解码器。

库里还提供可选的 transport 接口。比如 pldm_transport_af_mctp_init() 创建 AF_MCTP 后端，pldm_transport_af_mctp_map_tid() 在本地登记 TID 与 EID 的对应关系，上层才可以按 Terminus 选择目的端。登记映射不会发出 PLDM SetTID，也不会改变远端 TID。翻代码时能搜到这些函数；要判断板上走没走这条路，还得看应用的链接清单。libpldm v0.13.0 的 transport 接口 · AF_MCTP 后端
