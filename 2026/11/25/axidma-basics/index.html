二、示例平台与数据路径

03 · 示例平台：DMA 资源与内部通路

虚构教学配置：1 个控制器、8 个通道。

资源 通道用途 每通道 FIFO
M2M 通道组 CH1～CH4 128 × 128 bit = 2 KiB
外设通道组 CH5～CH8 16 × 128 bit = 256 B

要点：8 个通道共享 AXI 访问接口；通道数量不等于接口数量。

本教学平台只有一个 AXIDMA 控制器，共 8 个通道。CH1～CH4 用于内存搬运，CH5～CH8 用于外设传输。M2P 表示内存到外设，P2M 表示外设到内存。

每个通道保存自己的配置和 FIFO。FIFO 是按先后顺序存取数据的缓冲区。M2M 通道每通道 128×128 bit，即 2 KiB；外设通道每通道 16×128 bit，即 256 B。

CPU 通过 32 bit APB 接口配置寄存器。DMA 经片内互连访问 1 MiB SRAM 和串行外设。AXI 数据宽度 128 bit、地址宽度 32 bit、ID 宽度 4 bit、LEN 宽度 8 bit。各通道共享访问接口。

源控制逻辑安排读取，数据进入通道 FIFO，目的控制逻辑安排写入。LLI 读取配置，状态与中断逻辑向 CPU 报告结果。外设请求与确认只控制搬运时机，不承载业务数据。以上均为虚构教学配置。

04 · DMA 内部各部分负责什么

数据读回后先进入通道 FIFO；读和写可以按各自进度工作。

工作 负责的部分 可以观察什么
接收配置 寄存器接口 SAR、DAR、CFG、CTL、CHEN
读取源数据 源控制逻辑、读仲裁、AXI 读接口 AR 请求与 R 数据
暂存数据 各通道 FIFO 读写进度与等待情况
写入目的区域 目的控制逻辑、写仲裁、AXI 写接口 AW、W 与 B 返回结果
读取下一份配置 LLI 控制逻辑与 AXI 读接口 指向描述符地址的读请求
报告结果 状态寄存器与中断逻辑 完成、错误、CPU 通知

要点：LLI 读取的是传输配置；普通读写通路搬运的是业务数据。

先把内部功能分清，再看总线信号。AR 是读地址通道，R 返回读数据；AW 是写地址通道，W 发送写数据，B 返回写操作的结果。它们是 AXI 的五组独立通道，不是五个 DMA 控制器。

源端读回的数据暂存在通道 FIFO 中。目的端可以一边写已有数据，源端一边继续读取后面的数据，不要求先把整块读完。读写位宽不同、目标响应速度不同，都可能使两侧进度暂时不同。

链表方式还会产生读取描述符的总线访问。定位波形时，应先按地址区分描述符和业务缓冲区，不能把所有 AR 请求都统计成源数据读取。单块方式没有这类描述符读取。

CPU 反复查询状态称为轮询；DMA 主动通知 CPU 称为中断。它们改变的是软件获取结果的方法，不改变业务数据路径。本表是功能划分，真实队列深度、流水级数及互连转换行为仍应以当前硬件设计和波形为准。

05 · 一次 SRAM→SRAM M2M：谁参与，数据怎么走

单块直接寄存器模式 · CH1 · 256 B 教学算例

要点：CPU 负责准备和验收；AXIDMA 经同一片互连完成读和写。

源、目的区域位于同一块 1 MiB SRAM，范围为 [0x20000000, 0x20100000)。图中两处片内互连是同一组件。源地址为 0x20001000，目的地址为 0x20002000，寄存器基地址为 0x40010000。

CPU 准备缓冲区、同步缓存，并通过 BSP 完成平台初始化。BSP 是负责平台相关配置的代码。随后配置地址、长度、搬运方式和状态使能，再开启通道。示例采用统一地址映射，CPU 和 DMA 使用相同的 SRAM 地址。

读地址从 DMA 发向 SRAM，读数据返回 DMA；写地址和写数据从 DMA 发向 SRAM，写响应返回 DMA。读后续数据和写已有数据可以重叠。单块 M2M 不使用外设握手，也不读取 LLI。

本例搬运 256 B，每项 4 B，共 64 项，因此 BLOCK_TS=63。两侧 MSIZE 字段写 3，对应内部正常请求的 16 项。读写长度使能均为 1，读长度配置为 7，写长度配置为 3。

若实际每笔读为 8 拍、写为 4 拍，则分别需要 8 笔读、16 笔写。这个条件算例不能反推出 MSIZE，也不代表硬件实测。完成后同步目的缓存并比较 256 B 数据。

06 · 把一次搬运对应到寄存器

先确定地址和数量，再设置方式、启动和结果通知。

要决定的事情 寄存器 / 字段 单块 M2M 的含义
从哪里读，写到哪里 SAR / DAR 填写 DMA 可访问的地址
共搬多少，每项多宽 BLOCK_TS / SRC、DST_TR_WIDTH 总量按源数据项计算
方向与后续块 TT_FC / SRC、DST_MULTBLK_TYPE M2M，双方单块；字段均为 0
地址和总线访问规则 SINC、DINC / MSIZE / AxLEN 内存地址递增；分别配置各类数量
允许控制器和通道工作 DMAC_CFG / CHEN + CH_EN_WE 先开控制器，最后启动通道
记录并通知结果 INTSTATUS_ENA / INTSIGNAL_ENA 状态记录与中断输出分别控制

要点：修改 CHEN 时必须同时设置对应的写使能位。

SAR 和 DAR 分别保存源、目的地址，示例代码分别写低 32 位和高 32 位。BLOCK_TS 以源数据项计数；数据项是按 DMA 传输位宽计算数量的单位，例如 32 bit 对应 4 字节。AXI 的“拍”则指数据通道完成的一次传输，一拍可能等待多个时钟周期。

示例单块接口固定 TT_FC=0，即由 DMA 控制的 M2M，并把源、目的 MULTBLK_TYPE 都设为 0。SINC/DINC 编码 0 表示地址递增。CFG_L 的多块方式与握手字段应按各自定义配置，不能混用。

DMAC_CFG 控制整个 DMA，CHEN 控制具体通道。CHEN 的写使能位使硬件接受这次修改，不能只对通道使能位做普通清零或置位。

INTSTATUS_ENA 控制事件是否记入状态，INTSIGNAL_ENA 控制是否对 CPU 输出中断。INTSTATUS 用来读结果；向 INTCLEAR 的相应位写 1 清除已处理事件，这叫 W1C。更多寄存器细节在单块、中断和参数章节分别展开，避免把所有字段一次堆在同一页。

CTL 中的 MSIZE 和 AxLEN 不能用同一种编码换算。MSIZE 参与源、目的内部请求的数据量组织；对应使能位置 1 时，配置的 AxLEN 给出希望采用的 AXI 长度。最终每笔访问的拍数以总线字段为准，详见第 12～17 小节。

三、AXI 基础：通道、握手与读写事务

07 · AXI：地址、数据和结果分开传

AXI 是片内组件之间的访问协议；这里讲支持 burst 的 AXI4 内存映射接口。

通道 内容方向 主要携带什么
AR：读地址 DMA → 目标 源地址、每拍大小、这笔读多少拍
R：读数据 目标 → DMA 读出的数据、响应状态、最后一拍标记
AW：写地址 DMA → 目标 目的地址、每拍大小、这笔写多少拍
W：写数据 DMA → 目标 写入的数据、有效字节、最后一拍标记
B：写响应 目标 → DMA 这一笔写访问的响应状态

要点：五个通道可以按各自进度工作；“独立”不代表没有先后约束。

DMA 是发起读写请求的一方，内存控制器或外设接口是接受访问的一方。AXI 规定双方如何交换地址、数据和结果，互连负责把请求送到目标。这里介绍 AXI4 内存映射接口，不是 AXI4-Lite 或 AXI-Stream。

一次读访问使用 AR 和 R，一次写访问使用 AW、W、B。每个通道都有自己的 VALID/READY，READY 方向与该通道内容的发送方向相反。读数据和写响应由目标发送，所以并不是所有 VALID 都由 DMA 驱动。

地址与数据分开，可以让不同通道重叠工作。一次地址请求还可以描述多拍数据，这称为 burst；一拍是数据通道完成一次握手的数据传输，不等于一个时钟周期。读写也可以同时推进。

各通道有依赖规则：读数据必须对应已接受的读请求；写响应必须等写地址和最后一拍写数据均已被接收后才能发出。AW 与 W 独立，不能笼统地要求写数据一定在写地址之后出现。后面的写波形只画一种合法顺序。

后续会介绍 LEN、SIZE、ID 和未完成事务，本小节只建立阅读波形需要的基础。

08 · VALID 与 READY：两者都为 1，才传成功

VALID：发送方有有效内容；READY：接收方现在能接收。

t1～t2：A 保持不变；t3 / t4 / t6：各接收一项。共三项，不是六项。

波形取值：每列为对应时钟上升沿的采样值。

信号 / 内容 t1 t2 t3 t4 t5 t6
VALID 1 1 1 1 0 1
READY 0 0 1 1 1 1
内容 A A A B — C
握手 — — A ✓ B ✓ — C ✓

要点：在时钟上升沿判断握手；等待期间保持 VALID 和对应内容不变。

波形中的 t1～t6 是采样上升沿，图中数值表示该沿到来时的信号。高低电平线在相邻采样沿之间变化，用于说明逻辑关系，不代表实际器件的延迟。下方表格提供同一波形的精确取值。

t1 和 t2 时 VALID=1、READY=0，A 尚未被接收，发送方必须保持 A 和 VALID。t3 两者同时为 1，A 才成功传输一次；t4 可以立即传下一项 B，所以 VALID 无需在连续两拍之间拉低。t5 没有有效内容，READY 即使为 1 也不产生传输。t6 接收 C。

发送方不能等待 READY 才开始宣告 VALID；否则双方互相等待可能无法推进。接收方可以暂时拉低 READY，这种让发送方等待的方式称为反压。VALID 已经拉高而没有完成握手时，不能提前撤回内容。

同样规则适用于五个通道。地址通道握手表示地址请求被接受，数据通道握手表示一拍数据被接受，写响应通道握手表示响应被接受，三者不能混为一谈。AXI 总线握手也不同于外设向 DMA 提交搬运请求的 REQ/ACK。

09 · 读波形：一笔地址请求，返回四拍数据

例：ARLEN=3、ARSIZE=2，地址对齐；4 拍 × 每拍 4 B = 16 B。

AR 在 t1 接收；R 在 t2 / t4 / t5 / t6 接收。t3 等待，不重复计数 D1。

波形取值：每列为对应时钟上升沿的采样值。

信号 / 内容 t1 t2 t3 t4 t5 t6
ARVALID 1 0 0 0 0 0
ARREADY 1 1 1 1 1 1
RVALID 0 1 1 1 1 1
RREADY 1 1 0 1 1 1
RLAST 0 0 0 0 0 1
RDATA — D0 D1 D1 D2 D3

要点：RVALID 高了几周期不是拍数；只数 RVALID 与 RREADY 同为 1 的上升沿。

例子使用 INCR 读访问，地址对齐，ARLEN=3 表示四拍，ARSIZE=2 表示每拍 4 B，总计 16 B。t1 接受一次 AR 请求，后面四拍都属于这个请求，不需要每拍重新发送 AR。为便于阅读，图中未展开 ARADDR 等内容字段；它们在地址请求等待期间同样需要保持稳定。

t2 接收 D0；t3 时 D1 已有效，但 RREADY=0，因此 D1 没有传成功。t4 必须仍提供 D1，此时完成第二拍；t5 完成 D2；t6 完成 D3。RLAST 在最后一拍 D3 对应的周期为 1，且 t6 同时发生数据握手，这笔读事务才完成。

如果最后一拍等待接收，RLAST 也需要与数据一起保持，不能把 RLAST 单独拉高就当成传输结束。目标可在数据拍之间插入无效周期，接收方也可暂停，所以四拍不保证四个时钟周期完成。

每拍还有 RRESP，用于报告响应状态，本图省略并假设均成功。拍数正确仍需检查响应、数据内容与地址。本例只是协议示意，不是硬件实测波形。

10 · 写波形：最后一拍之后，还要等响应

例：AWLEN=1，两拍写数据；AW、W、B 各自完成握手。

t3：最后一拍写数据被接收；t5：响应等待；t6：接收写响应，事务完成。

波形取值：每列为对应时钟上升沿的采样值。

信号 / 内容 t1 t2 t3 t4 t5 t6
AWVALID 1 0 0 0 0 0
AWREADY 1 1 1 1 1 1
WVALID 0 1 1 0 0 0
WREADY 1 1 1 1 1 1
WLAST 0 0 1 0 0 0
BVALID 0 0 0 0 1 1
BREADY 1 1 1 1 0 1
WDATA — D0 D1 — — —

要点：WLAST 表示最后一拍写数据；BVALID 与 BREADY 握手后，这笔写事务才完成。

本图是一种合法的 AXI4 写访问：t1 完成写地址握手，t2 完成 D0，t3 完成 D1 且 WLAST=1。t4 目标尚未给出写响应，事务仍未完成；t5 给出响应但 BREADY=0，响应还未被接收；t6 才完成 B 握手。

图中 BVALID 在 t5～t6 保持为 1，对应 BRESP 也必须保持。假设 BRESP=OKAY，则表示总线写访问成功；若返回错误仍是一个已返回的响应，软件需要检查错误，而不是仅凭握手认定业务成功。

AW 与 W 是独立通道，图中先地址后数据只是一种情况；写数据也可以先于地址或同时被接收。目标只有在写地址和最后一拍写数据都完成握手后，才可给出写响应。不能把本图的时钟间隔当成固定延迟要求。

每个数据拍还通过 WSTRB 指出哪些字节有效，本图省略并假设本次传输的所有数据字节均有效。一次 burst 对应一个写响应，不是每拍一个 B 响应。DMA 完成还涉及该任务的其他读写请求、控制状态和错误；单笔 AXI 写完成也不等于 CPU 缓存已经同步。

四、参数计算：BLOCK_TS、位宽、MSIZE 与 AxLEN

11 · 先算总量：BLOCK_TS 按源数据项计数

适用于本次讲解的对齐、由 DMA 控制长度的 M2M 传输。

总字节数 = (BLOCK_TS + 1) × 2^SRC_TR_WIDTH

传输位宽

  • 编码 0 / 1 / 2 / 3 / 4
  • 对应 1 / 2 / 4 / 8 / 16 B

256 B，源宽 32 bit

  • 每项 4 B，共 64 项
  • BLOCK_TS 写 63

目的位宽可以不同

  • 总量仍按源数据项计算
  • 两侧最终字节数必须一致

要点：接口传 block_items；驱动写 BLOCK_TS = block_items − 1。

先选择源传输位宽，再把总字节数除以每项字节数。源宽 32 bit 时，每项为 4 B；256 B 对应 64 项，写入寄存器的值为 63。不要把 256 直接写入 BLOCK_TS，也不要把已经减一的 63 再交给 block_items 参数。

SRC_TR_WIDTH 和 DST_TR_WIDTH 是编码，不是直接填写 32 或 128。编码值 n 表示每项 2^n 字节；代码中的常量名能帮助避免单位混淆。示例直配接口对 block_items 的检查范围是 1～0x40000。接口允许的数值仍需满足当前通道和总线的硬件能力。

源、目的位宽可以不同。例如源宽 32 bit、目的宽 128 bit，搬 256 B 时仍是 64 个源数据项，而目的端对应 16 个 16 B 数据项。总量不会因为目的端变宽而扩大。

BLOCK_TS 的读写含义还要区分时机：启动前写入的是源数据项总数减一；运行时读回表示已从源读取的数据项数。不能用运行中的读回值直接当作剩余数量，或据此认为软件配置被错误覆盖。

12 · MSIZE：一次内部请求处理多少项

M2M 中，DMA 分次组织读取和写入；每次内部请求处理的数据量由 MSIZE 参与确定。

看哪个参数 表示什么 怎样计算
SRC_MSIZE 源端内部请求的数据项数 每项大小由 SRC_TR_WIDTH 决定
DST_MSIZE 目的端内部请求的数据项数 每项大小由 DST_TR_WIDTH 决定
数量与字段编码 1 / 4 / 8 / 16 项 依次写编码 0 / 1 / 2 / 3
MSIZE 对应 16 项 每项 4 B：一次正常请求为 64 B 若每项改为 16 B，则为 256 B
与整块数量的区别 BLOCK_TS 管整块；MSIZE 管内部请求 块尾不足完整批次时，处理剩余量

要点：先用 MSIZE 和位宽计算内部请求的数据量，再用实际 LEN 核对总线拍数。

本节只讨论内存到内存的 M2M。DMA 将整块数据分次读取、分次写入。这里把 DMA 内部一次安排读取或写入的操作称为“内部请求”；SRC_MSIZE、DST_MSIZE 分别参与确定两侧一次内部请求处理多少个数据项。

数据项有多大，由对应侧的传输位宽决定。源端位宽为 32 bit、SRC_MSIZE 对应 16 项时，一次正常内部读请求的数据量为 16×4=64 B。目的端也按自己的 DST_TR_WIDTH 和 DST_MSIZE 计算。若目的端每项为 16 B，同样 16 项便是 256 B，因此比较两侧数量前应先换算成字节。

MSIZE 字段使用编码值：0、1、2、3 分别表示 1、4、8、16 项。例如希望每次处理 16 项，应写编码 3，而不是把数字 16 直接写进字段。后面的“MSIZE 对应 16 项”都指解码后的数据项数。

BLOCK_TS 与 MSIZE 分工不同：前者指定整块有多少个源数据项，后者参与内部请求的数据量安排。例如整块有 40 项，MSIZE 对应 16 项，处理到块尾时只剩 8 项，就应处理这 8 项，不能为了凑满 16 项而多搬数据。

内部请求的数据量还要通过 AXI 访问完成，一次内部请求可能对应多笔 AXI 访问。因此，MSIZE 对应 16 项，不等于每笔总线访问必然是 16 拍；第 14 小节用 16 项分成两笔 8 拍说明这种关系。

改变 MSIZE 会改变内部请求的数据量安排，也可能影响等待和吞吐。是否更快，需要在相同总量、位宽和运行条件下比较完成时间，不能只根据数值大小判断。

AxLEN 是 ARLEN 与 AWLEN 的统称：ARLEN 用于读请求，AWLEN 用于写请求。两者都使用“拍数减一”的编码，字段值 0、3、7、15 分别对应 1、4、8、16 拍。软件写入通道 CTL 的配置值和总线上每笔请求携带的 LEN，要分开看。

对应 LEN_EN=1 时，DMA 在条件允许时采用配置长度。例如 ARLEN_EN=1、配置 ARLEN=7，表示希望采用 8 拍读访问。块尾只剩少量数据、下一笔访问会跨过 4 KiB 边界，或者硬件容量不足，都可能使实际访问变短。

对应 LEN_EN=0 时，由 DMA 在通道硬件上限内自动选择可行长度。这个上限是硬件设计时确定的能力；自动模式不保证每笔都取最长，也不表示总线接收方替 DMA 选择长度。DMA 仍然先生成请求，再把实际 LEN 发给总线。

读侧准备访问时，还要把期望拍数与 FIFO 总容量按源端传输宽度折算后的项数比较。假设一项对应一拍、每项 4 B，期望访问 8 拍，但 FIFO 总容量只有 16 B，只能容纳 4 项，读侧就先按 4 拍准备访问。这是便于理解容量限制的假设例子；本教学平台 M2M 通道的 FIFO 总容量是 2 KiB。

这里比较的是 FIFO 总容量，不是此刻还剩多少空位。总容量属于通道的硬件配置，空位随读写进度变化。读侧准备的长度也不代表请求已经发出；DMA 发出请求前还要处理剩余数据和地址边界等条件。因此，不能用某一时刻的空位数直接推算实际 LEN。

无论长度怎样选择，实际请求一旦被总线接收，就必须按它携带的 LEN 完成传输。例如软件期望 8 拍，而某笔实际请求携带 LEN=3，那么这一笔必须完成 4 拍。源、目的两侧分别配置和观察，搬运的总字节数相同不要求两侧每笔拍数相同。

MSIZE 继续参与内部请求的数据量安排；使能指定长度并不会取消它的作用。MSIZE 回答内部一次请求处理多少项，配置 AxLEN 回答希望一笔 AXI 访问采用多少拍，实际总线 LEN 则记录这一笔确定的拍数。

要点：只有 VALID 与 READY 同时为 1，才算完成一次地址或数据传输。

看波形时，先用 ARVALID && ARREADY 找到被接收的读地址，记录 ARADDR、ARLEN、ARSIZE 和 ARID，再按相应 ID 统计 RVALID && RREADY 的数据拍。最后一拍的 RLAST 必须与数据一起被接收。RVALID 保持了几个周期，不等于传了几拍。

写地址 AW 和写数据 W 使用不同通道，不应要求它们同一周期出现。写数据完成后还要收到 B 响应，才能知道这笔写访问的返回结果。仅看到 WLAST 不能证明整笔写访问已经结束，也不能直接当作整个 DMA 完成。

接收方用 READY=0 要求发送方等待，通常称为反压。等待期间，发送方保持尚未被接收的有效数据或地址控制字段。已经发出的请求不能靠提前给 LAST 来减少约定拍数。

AXI 总线上没有 MSIZE 或 AxLEN_EN 信号；它们属于 DMA 配置。NoC 接收到的是已经生成的地址、实际 LEN、SIZE、ID、属性及读写数据。假设一次 M2M 的块尾最终发出 LEN=2，总线就按 3 拍完成，即使软件此前配置的 LEN 是 7。这里以已知实际字段解释协议，不推断该块尾必定怎样拆分。

判断 DMA 怎样选择长度，应在 DMA 接入 NoC 的接口观察。若 NoC 或总线桥转换位宽或拆分访问，两侧的访问次数可能不同，需要分别核对有效数据总量。NoC 的重排能力不能用来推断 MSIZE 的含义或内部请求分组。

软件配置值说明希望怎样访问，实际 LEN 与数据握手说明这一笔怎样完成。每次记录应同时保存通道 CTL、读写地址与宽度、实际 LEN、LAST 和返回状态。

五、单块 M2M：从准备到验收

18 · 启动前，先把内存和地址准备好

基础用例先验证 CPU 能正常读写，再验证 DMA 搬运。

  1. 选择缓冲区：确认属于可用 SRAM，源、目的不重叠，并满足位宽和缓存行要求。
  2. CPU 预检查：填充源数据，写读目标区域并比较；随后清零目的区域。
  3. 转换 DMA 地址：调用平台地址转换接口，保留 CPU 指针与 DMA 地址用于诊断。
  4. 同步缓存：启动前同步源、目的区域；传输期间 CPU 不修改源或访问目的区。

要点：CPU 指针用于 CPU 访问；SAR / DAR 使用 BSP 转换后的 DMA 地址。

CPU 预检查将普通内存访问问题与 DMA 问题分开。若 CPU 对目标 SRAM 的写、读和比较就已经失败，应先检查内存区域、访问权限或平台状态，而不是继续调整 DMA 参数。

示例基础用例使用专用工作区，并在 CPU 预检查后清空目的区域。源、目的模式应不同且容易区分，例如源按字节递增、目的先填固定值，这样能看出“没有写入”“只写了部分”和“地址偏移”三类现象。

示例平台采用统一地址映射，CPU 地址与 DMA 总线地址相同。软件仍通过 BSP 地址转换接口传递地址，便于适配不同平台。实际硬件是否存在地址转换或别名，需要单独确认。

同步缓存和地址转换是不同工作：前者使内存与 CPU 缓存中的数据一致，后者使 DMA 访问正确地址。两者都正确后再启动。缓冲区生命周期必须持续到 DMA 确认停止；函数返回错误并不自动表示 DMA 已经不再访问这段内存。

  • 写 LEN=3 → 4 拍
  • 最终分组以实际请求为准

要点：block_items 填实际项数；MSIZE 和 burst_len 填各自字段编码。

示例用于把第 12～17 小节的参数对应到示例 direct 接口。源、目的都按 32 bit 传输，block_items=64，整块 256 B。MSIZE 字段写 3，对应正常内部请求的 16 项；长度字段分别写 7 和 3，对应期望读 8 拍、写 4 拍。配置表达期望，不能据此保证实际分组与第 17 小节完全相同。

本节省略了平台初始化、缓冲区准备、结构体其他字段、错误处理与启动操作，不是可直接执行的完整程序。正式使用时应先将完整结构体清零，再用对应枚举配置 priority、clear_status、allow_unaligned 等字段。

axidma_direct_channel_config_internal 检查参数后，设置 M2M、单块方式与优先级，写入 SAR/DAR、BLOCK_TS、CTL 的位宽与 MSIZE，再按开关更新长度字段，最后配置状态记录和中断输出。这里仅修改教学材料，没有修改驱动。

configure_burst_len=true 才更新 CTL_H 中这组长度字段。两个 enable 再分别决定读写侧是否指定长度。传入 src_burst_len=7 就写 7，驱动不会再次减一。configure_burst_len=false 表示本次不更新，不表示硬件使能位一定是零；复用通道时要检查已有配置。

若明确需要自动长度选择，在通道停用、符合配置时序的前提下，将 configure_burst_len 设为 true，两个 burst_len_enable 设为 false，使驱动清除对应使能位。关闭使能仍不取消 MSIZE 的内部请求作用。

按 64-bit CHx_CTL 编号，ARLEN_EN 位于 bit 38、ARLEN 位于 bits 46:39，AWLEN_EN 位于 bit 47、AWLEN 位于 bits 55:48。代码访问高 32 位 CTL_H 时，对应 bit 6、bits 14:7、bit 15、bits 23:16。MSIZE 位于 CTL_L，另行写入。普通 direct 接口没有独立 OSR 上限配置参数。

验证这组参数时，先核对寄存器读回，再按第 16 小节记录 DMA 侧实际地址请求和数据握手。内存最终比较正确只能证明数据结果，不能单独证明每笔长度。

本副本中的代码和函数名用于表达配置顺序与接口契约，不构成可直接运行的驱动交付。实际接口需按目标驱动适配。

20 · 配置完成后，再启动并等待结果

把控制器初始化、通道配置、启动和等待分开检查。

  1. 初始化控制器：BSP 开启时钟并复位；axidma_controller_enable() 开启 DMA。
  2. 配置当前通道：写地址、数量和规则；清旧状态；轮询路径关闭中断输出。
  3. 最后启动：axidma_channel_start() 同时写通道使能位和对应写使能位。
  4. 有限时间等待：axidma_channel_wait_poll() 检查完成与错误，并保存诊断状态。

要点：等待必须有超时；超时只说明软件未等到结果，不证明硬件已停止。

示例 axidma_controller_enable 写 DMAC_CFG=0x3，同时使能 DMA 和控制器全局中断能力。轮询路径仍通过通道 INTSIGNAL_ENA=0 阻止中断输出，不能只看全局 INT_EN 就断定 CPU 一定收到中断。

参数和缓存准备完成后再开启通道。CHEN 使用写使能机制，软件必须在同一次写入中给出要修改的通道位和相应 WE 位。各通道组的寄存器位置应由驱动处理，应用不宜凭通道号自行拼接所有寄存器。

轮询过程读取状态，发现错误或完成后返回，等待到上限仍无结果则报告超时。状态清除应在保存所需信息后进行，否则后续调试可能只看到已经清零的寄存器。

错误路径特别容易混淆“等待结束”和“硬件停止”。传输未完成时，必须按硬件规定停止通道并确认没有后续访问，才可复用缓冲区或复位资源。示例普通 cleanup 不能作为已验证的在途停止方案；本次分享不把常规退出等同于完整的安全终止测试。

21 · 完成后，检查状态，也检查数据

一次可解释的结果至少包含配置、状态、数据和测试环境。

硬件结果

  • 确认最终完成状态
  • 确认没有通道错误

CPU 可见的数据

  • 先 sync_for_cpu，再比较目的数据
  • 必要时检查前后保护区域

失败证据

  • 记录首个错误偏移与期望 / 实际值
  • 保存 SAR、DAR、CTL、CFG 和状态

退出与复用

  • 清已处理事件，关闭本次通知
  • 确认通道停止，再复用资源

要点：“DMA 完成”与“CPU 已经读到正确数据”需要分别确认。

正常完成后调用 axidma_bsp_sync_for_cpu，使 CPU 随后读取目的区域时取得 DMA 写入的内容。再逐项比较，首次不一致的位置比“比较失败”四个字更有帮助：开头就错、固定周期错误、只错尾部，通常指向不同方向。

检查传输是否超出范围时，可在目标区域前后布置保护数据。有效区域全对而保护区被改写，说明测试仍然失败。并非当前所有基础用例都具备这种检查；设计新验证时应按需要补充。

寄存器和返回码要和同一次传输对应。建议记录通道号、CPU/DMA 地址、总字节数、位宽、MSIZE、LEN 配置，以及出现错误时的原始状态。环境信息应包含固件版本、芯片或仿真平台版本和运行命令。

共享控制器下，退出不能随意复位整块 DMA，否则会影响其他通道。示例 BSP 的 prepare/release 面向整个控制器，并不是带引用计数的多客户端管理器。应用应明确谁负责控制器生命周期。

六、LLI 与多块传输

22 · LLI 把多段配置放进内存

LLI 是描述符：保存一段搬运的地址、长度、规则和下一项位置。

描述符 0

  • 源 A → 目的 A
  • 32 B
  • LLP 指向描述符 1

描述符 1

  • 源 B → 目的 B
  • 32 B
  • LLP 指向描述符 2

描述符 2

  • 源 C → 目的 C
  • 32 B
  • LAST=1，结束

连接顺序：描述符 0 → 描述符 1 → 描述符 2；最后一项 LAST=1。

要点：CPU 先准备整条链，DMA 再依次读取并执行。

单块方式需要 CPU 对每一段搬运重新配置寄存器。LLI 方式把多段配置预先写入内存，DMA 读取一份描述符，完成相应搬运，再根据 LLP 找下一份。这样可以组织多段地址不同的数据，减少 CPU 逐块介入。

LLP 是“下一份描述符的地址”，不是下一段业务数据的地址。描述符内部的 SAR 和 DAR 才指向源、目的缓冲区。因此检查链表时，要分别检查描述符地址和数据地址。

图中是三段 32 B 的简化示意，便于看出连接关系；示例普通 sram_lli_smoke 用例是四个描述符，每个 32 B，总共 128 B。IOC 关闭用例又使用一项和三项两种情况，不能把不同用例的长度混在一起。

教学示例主要验证有限长度的链。把最后一项指回第一项，还不足以形成可用的持续接收环形缓冲；后者还需要描述符更新、生产与消费位置、回绕和并发访问规则，本次不把这些能力视为已实现。

23 · 描述符里保存了哪些字段

示例代码按 64 B 对齐和分配描述符；偏移以描述符起始地址为基准。

偏移 字段 用途
0x00 SAR 这一块的源地址
0x08 DAR 这一块的目的地址
0x10 BLOCK_TS 源数据项数减一；0x14 为保留位置
0x18 LLP 下一份描述符的 DMA 地址
0x20 CTL 位宽、MSIZE、VALID、LAST、IOC 等
0x28 / 0x2C / 0x30 SSTAT / DSTAT / LLP_STATUS 可选状态相关区域；本实例未启用状态写回

要点：分配空间和字段偏移都要正确；不能把 C 结构体布局想当然地当成硬件格式。

手册给出的描述符以 64-bit 地址字段组织，SAR、DAR、LLP 都不能因为 CPU 某段地址较小就只填低位。BLOCK_TS 虽然是 32-bit 字段，后面仍有保留位置，不能直接把 LLP 紧接在它后面。

示例实现使用 64 B 的描述符槽位并满足 64 B 对齐，基本搬运配置位于前 40 B。描述符要位于 DMA 可读的内存，LLP 保存转换后的 DMA 地址；CPU 构建描述符时使用的是 CPU 可访问的指针。

CTL 的高位包含 LLI_VALID（bit 63）、LLI_LAST（bit 62）和 IOC_BlkTfr（bit 58）。按高 32 位查看时，分别是 bit 31、30 和 26。调试日志必须先分清是在看完整 64 位字段，还是 CTL_H。

描述符中存在状态区域，不代表每个平台都启用写回。本教学配置明确关闭描述符状态写回，LLP_STATUS 保持初始化值并不表示搬运失败。第 48 小节用此配置说明如何选择验收条件。

24 · VALID、LAST、IOC 分别解决什么问题

是否可读取、是否还有下一块、是否报告块完成，是三件不同的事。

VALID：本项已准备好

  • DMA 可以使用这份描述符
  • 先完成字段与缓存同步，再交给 DMA

LAST：这是最后一项

  • 这一块完成后结束整次传输
  • 不能只依赖 LLP=0 推断结束

IOC：报告块完成

  • 按配置产生块完成状态 / 通知
  • 不要与全链完成混为一谈

交付描述符的顺序

  • 准备数据 → 构建全部字段
  • 同步缓存 → 保证顺序 → 启动

要点：IOC 影响块完成事件；关闭 IOC 不等于取消最终 DMA 完成。

VALID 表示描述符中的配置已经可用。准备描述符时，先写好地址、长度、下一项指针和其他控制字段，确保 DMA 看到的是完整内容。示例有限链在启动前准备完毕，并同步描述符缓存；不能在 DMA 可能读取时随意修改其中一部分。

LAST 明确指出最后一个块。LLP 是下一项指针；结束条件应按手册和示例实现设置 LAST，不能仅凭链尾指针为零就假定所有控制位都不需要配置。

IOC_BlkTfr 控制块完成事件。若软件要接收中断，还要相应的状态使能、信号使能和 CPU 中断配置。最后的 DMA_TFR_DONE 表示整次 DMA 传输完成，与某一块的 BLOCK_TFR_DONE 含义不同。

fence 用来约束 CPU 访问先后顺序，但不会替代缓存写回。链表地址与业务数据地址都正确，仍可能因为 DMA 读到了旧描述符而失败。若要动态更新未就绪描述符，还需要单独遵守硬件暂停、有效位更新和恢复流程；这里不把静态链的步骤扩展为未经验证的动态用法。

25 · 沿着示例代码看一次链表传输

示例 LLI 用例使用 CH1；完整生命周期由 LLI 实现管理。

  1. 准备链和数据：分配对齐描述符；填写各块地址与长度；连接 LLP，设置末项 LAST。
  2. 配置通道：两端 MULTBLK_TYPE=3；LLP 指向首项；配置完成和错误事件。
  3. 同步后启动：同步数据与描述符缓存；硬件先取配置，再搬运对应数据。
  4. 等待并验收：检查最终完成与错误；同步目的区；逐块比较，随后退出。

要点：描述符读取、数据搬运、最终完成，应分别检查。

示例 LLI 路径固定使用 CH1，源、目的多块类型都配置为链表方式，即编码 3。LLP 保存第一份描述符的位置；后续配置从描述符中加载，不能只观察启动前的通道寄存器就推断所有块的地址与长度。

LLI 实现拥有自己的 BSP 和 IRQ 初始化、释放流程，而部分 direct 用例由命令包装层负责这些操作。复用函数时需要先确认生命周期由谁负责，避免重复复位控制器或在已经关闭时钟后访问寄存器。

示例 LLI 配置会设置源、目的 OSR 上限为 16（字段编码 15）。虽然配置结构中有 burst_len 相关成员，但示例参数校验会拒绝 configure_burst_len=true，因此不能宣称 LLI 已经支持用户指定 ARLEN/AWLEN。普通单块路径对此有独立支持。

验收应覆盖每块数据、最终状态和通道退出。若第二块开始出错，优先检查下一项 LLP、描述符偏移、缓存同步和本块长度；如果第一项就无法取到，再检查首项地址、对齐、VALID 和读响应。不要只延长等待时间而不检查访问是否发生。

26 · 其他三种多块方式，知道区别即可

四种多块方式是 Contiguous、Auto Reload、Shadow、LLI；单块单独使用。

方式 下一块怎样开始 理解重点
Contiguous 地址沿上一块继续 连续一侧沿用进度，不等于所有字段都自动变化
Auto Reload 重新使用已保存的起始配置 适合重复同一段；结束时机需要严格处理
Shadow CPU 提前写好下一块配置 硬件在块边界采用新配置，软件要及时更新
LLI DMA 从内存读取下一份描述符 适合预先组织多段任务；本次重点

要点：本次重点掌握单块与 LLI；其余方式只理解下一块参数从哪里来。

四种多块方式都用于连续执行多个数据块，但下一块参数的来源不同。LLI 从内存描述符读取；其他方式通过连续地址、重载或影子配置提供下一块参数。

本分享重点讲单块与 LLI。其他方式仅比较用途，不提供完整编程序列。使用重载方式时，应核对终止步骤、最后一次块事件、通道停止和保护区数据，防止多执行一个块。

七、AXI 波形、边界与传输效率

27 · 读波形：数成功传输，不数等待周期

示意：ARLEN=3，共 4 拍；下图从该读请求的数据返回阶段开始。

周期 1 2 3 4 5 6
RVALID 1 1 1 0 1 1
RREADY 1 0 1 1 1 1
RDATA D0 D1 D1 — D2 D3
RLAST 0 0 0 — 0 1
累计接收 1 1 2 2 3 4

波形说明：只有周期 1、3、5、6 发生 RVALID 与 RREADY 同时为 1 的数据握手；累计接收四拍。

要点：周期 2 的数据尚未被接收，周期 3 接收后才计为第 2 拍。

这是一组人为构造的教学时序，不是硬件抓图。假设一个 ARLEN=3 的读请求已被接收，随后应该有四次有效的数据握手。周期 1 接收 D0；周期 2 虽然 RVALID=1，但 RREADY=0，所以没有接收 D1；周期 3 才真正接收它。

等待期间 D1 和相关有效字段保持稳定。周期 4 的 RVALID=0，此时 RDATA 与 RLAST 不参与有效传输，图中用横线表示不关心。周期 5 接收 D2，周期 6 接收带 RLAST 的 D3。

实际抓图还要核对 RID 和 RRESP。若多个读事务同时存在，先按 ID 与对应请求匹配，再统计每个事务。只对整个 R 通道数四个 RVALID 周期，会把等待或其他事务的数据混入。

写侧使用相同的 VALID/READY 计数规则。W 通道最后一拍标记 WLAST，但还需要等待 BVALID && BREADY；遇到写入结果异常时，应保存 BRESP，而不是只看数据是否已经送完。

28 · 128-bit 总线，不代表每拍都搬 16 B

访问位宽由 AxSIZE 描述；物理数据总线宽度只是可用的最大宽度。

物理总线

  • 128 bit = 16 个字节通道
  • 不能直接乘总线周期数算有效字节

一次较窄访问

  • AxSIZE=2：每拍访问 4 B
  • 即使 RDATA / WDATA 仍有 128 bit

写字节使能

  • WSTRB 每一位对应一个字节
  • 地址决定这次使用哪些字节位置

波形检查

  • 对照 ADDR、SIZE、DATA、STRB
  • 确认有效字节位置和目的数据一致

要点：计算有效数据量时，同时看 SIZE、地址和写字节使能 WSTRB。

当传输位宽小于物理数据总线宽度时，通常称为窄传输。比如 128-bit 总线每拍可以承载 16 B，但 AWSIZE=2 表示本次写访问每拍只有 4 B，不能因为 WDATA 有 128 位就把它算成 16 B。

以对齐的 4 B INCR 写访问为例，地址低四位为 0、4、8、12 时，16-bit WSTRB 可以依次对应 0x000F、0x00F0、0x0F00、0xF000。这个例子说明字节位置随地址变化；实际还需结合突发类型和具体访问情况核对，不能用固定掩码检查所有场景。

读通道没有 WSTRB 这样的写字节使能。读取哪些字节位置由地址和访问宽度确定。对总线之外的 CPU 数据比较，应以目标内存中的有效字节为准。

本教学配置只演示合法对齐地址。实际平台的非对齐能力应单独确认，不能从一个用例通过推导所有位宽和地址组合都受支持。

29 · 跨 4 KiB 时，要先拆成合法请求

合法拆分示例：每拍 16 B，从 …0FF0 搬 64 B；边界前 16 B，边界后 48 B。

事务 起始地址 拍数 / LEN 字节数
第 1 笔 …0FF0 1 拍，LEN=0 16 B
第 2 笔 …1000 3 拍，LEN=2 48 B

地址关系：…0FF0 → …0FFF 为边界前的 16 B；…1000 → …102F 为边界后的 48 B。两笔访问合计 64 B。

要点：4 KiB 限制针对每一笔 AXI 事务；整个 DMA 块可以跨边界。

4 KiB 边界是地址低 12 位从 0xFFF 回到 0 的位置。起始地址为 …0FF0 时，到边界只剩 16 B；若每拍访问 16 B，第一笔最多容纳一拍。剩余 48 B 可以从 …1000 开始用三拍完成。

本图展示一种合法拆分，不断言硬件一定选择这两笔；在其他内部条件限制下，也可能分成更多合法访问。判断重点是每一笔请求都不跨越边界，所有请求累计有效字节数等于 64 B。

DMA 应在地址请求发出之前完成拆分。若在 DMA 主接口已经抓到跨 4 KiB 的非法 burst，不能解释成“后面的 NoC 会把它处理好”。互连转换不能使上游违反协议的请求自动变成合规。

源、目的地址各自有边界，即使读侧不需要拆分，写侧也可能需要。用于验证的源、目的偏移要分别设计，并在目标前后增加保护数据。当前基础缓冲区按 4 KiB 对齐，不等于已经覆盖了跨边界场景。

30 · Outstanding：已经发出、尚未完成的事务

它按事务计数，不按数据拍计数；用于让后续请求提前发出。

读侧计数

  • +1：ARVALID && ARREADY
  • −1：RVALID && RREADY && RLAST

写侧计数

  • +1：AWVALID && AWREADY
  • −1：BVALID && BREADY

要点：写事务收到 B 响应后才完成，不能在 WLAST 时扣减。

Outstanding 表示已被接收但还没有全部完成的请求。假设连续接收了三笔 AR，此时尚未返回任何最后一拍，则读侧 outstanding 为 3。每接收一笔读事务的最后一拍减一；中间数据拍不能减少这个计数。

写侧从 AW 被接收开始计数，到 B 响应被接收结束。写数据发送完后，目标仍可能没有返回响应，所以 WLAST 与写 outstanding 减一不是同一个时刻。正常观测时以同一接口上的完整事务为统计范围。

SRC_OSR_LMT 和 DST_OSR_LMT 使用减一编码，手册字段上限对应 16 笔。示例 LLI 路径配置为 16，普通单块接口没有独立的 OSR 配置参数。通道上限与互连中的总容量是不同概念，应分别确认。

ID 不是“一笔事务占一个唯一槽位”。同一 ID 可以有多笔事务，并须满足同 ID 的顺序规则；不同 ID 可能允许不同完成顺序，但不表示硬件一定重排。ID 宽度也不能直接转换成实际可同时发出的事务数。

固定总量、地址与位宽，分别调整 MSIZE、LEN 或 OSR，再记录实际请求。

要点：较大的 LEN 或 OSR 不一定更快；目标响应和 FIFO 也会限制进度。

MSIZE 改变内部请求的数据量组织；配置 AxLEN 改变希望采用的总线访问长度；outstanding 表示已经发出但尚未全部完成的请求数量。三者对应不同控制因素，不能用一项的配置值替代另一项的观测。

只有实际 burst 变长时，同样数据量才可能对应更少的地址请求。仅把配置 LEN 调大，若受内部容量、块尾或地址边界限制，实际访问可能没有变化。更多 outstanding 可以使硬件在前一笔尚未返回时继续发请求，但收益仍取决于 FIFO、队列与目标响应。

测试时固定总量、地址、位宽和其余配置，每次只改变一个参数。记录 CTL 读回、实际 ARLEN/AWLEN 分布、地址请求数、READY 等待、未完成请求峰值和完成时间。现有资料不能给出 M2M MSIZE 的通用最优值，也不能保证越大越快。

只量启动到 DMA 完成，得到的是传输阶段时间；包含缓存同步、配置、中断和比较，则是软件端到端时间。重复样本必须使用相同口径，再以有效字节数除以时间计算吞吐。数据正确是前提，不能用数据 PASS 替代波形和性能记录。

长度可选择一项、恰好一笔、比一笔多一项和跨 4 KiB 等代表值。位宽和地址组合先满足当前实例能力，避免非法组合使性能比较失去意义。

要点：阈值决定何时请求；MSIZE 决定本批项数。握手不能弥补错误的数量配置。

本节只讨论外设 DMA 的请求和确认，不是说所有 DMA 传输都必须使用外设握手。M2M 通常不需要外设请求，仍然通过总线自己的握手完成访问。

外设收发数据与 DMA 访问总线的速度不同。CPU 给出 FIFO 数据端口地址和整块长度之后，DMA 仍不能仅靠这些配置知道外设当前是否有数据可读、是否有空位可写。硬件握手把外设的准备情况通知 DMA，避免软件必须不断轮询 FIFO 再安排搬运。

M2P 场景下，外设发送 FIFO 的空位达到请求条件，外设向 DMA 发出 TX 请求，DMA 才安排向发送端口写数据。P2M 场景下，接收 FIFO 的已有数据达到请求条件，外设发出 RX 请求，DMA 才安排读取接收端口。两种方向的 REQ 都由外设发向 DMA，不随数据方向反转。DMA 仍可能因为总线仲裁等原因稍后才服务，因此握手不能保证没有服务延迟。

REQ 是请求信号，ACK 是确认信号。本教学模型采用请求／确认协议：外设保持请求，DMA 完成本次请求对应的数据访问后确认；具体撤销顺序在下一页展开。ACK 不表示整块传输已经完成，也不表示串行线路已经发送结束。握手信号本身不携带业务数据，实际数据通过总线访问 FIFO 数据寄存器。

请求也不等于实时传送 FIFO 数量。阈值决定何时有资格发出请求，MSIZE 配置规定一次批量请求对应的数据项数。本节假设一个 DMA 数据项对应一个外设 FIFO 条目。TX 必须保证空位不小于 DST_MSIZE 对应项数，RX 必须保证已有数据不小于 SRC_MSIZE 对应项数。只有四项就发请求，却把 MSIZE 配成八项，握手接线正确也不能使缺少的四项自动出现。

外设 REQ/ACK 与 AXI VALID/READY 解决的问题不同：前者用于外设传输请求，后者确认某条总线通道的一次传输是否被接收。某些外设或桥接接口也会在 FIFO 空或满时阻止数据访问，但是否这样做取决于具体设计。不能仅凭总线访问成功，就认定读到的是有效接收数据；也不能笼统地认为 READY 与 FIFO 状态完全无关。

没有硬件外设握手时，可以在硬件与驱动支持的前提下由软件查询状态并安排访问，或依靠明确规定的总线等待机制。但不能把已经设计为硬件握手的传输随意关掉请求控制后直接运行。本节的批量示例不代替后续的服务延迟和单项尾部检查。

34 · 外设发出请求后，DMA 怎样回应

以下采用 串行外设 硬件握手，由 DMA 控制块长度；先看一次完整的批量请求。

图中标注与动作顺序：

  • AXIDMA
  • 按 MSIZE 对应的项数搬运
  • 外设 FIFO
  • TX 看空位，RX 看已有数据
  • 请求 REQ：外设 → DMA
  • 确认 ACK：DMA → 外设
  • 数据经总线访问：TX 为 DMA → FIFO；RX 为 FIFO → DMA
  • REQ↑ → 本次数据访问完成 → ACK↑ → REQ↓ → ACK↓
  • ACK 撤销后，再检查阈值，决定是否发出下一次请求。

要点：REQ 必须保持到 ACK；阈值变化不能中途取消本次请求。

先分清两件事：握手线传递“现在可以搬一批数据”的请求和完成确认；真正的数据通过 DMA 对外设数据寄存器的总线读写传输。TX 和 RX 都由外设向 DMA 发请求，但数据方向相反。发送时 DMA 往 TX FIFO 写，接收时 DMA 从 RX FIFO 读。REQ、ACK 是这里对相应 dma_tx_req/dma_rx_req 和 dma_tx_ack/dma_rx_ack 的简称。

外设侧需要开启 SERIAL_DMA_CTL_REG 的 TX_DMA_EN 或 RX_DMA_EN。DMA 侧需要选择硬件握手、正确的 SRC_PER/DST_PER 编号和传输方向；M2P 的外设在目的端，数量看 DST_MSIZE，P2M 的外设在源端，数量看 SRC_MSIZE。寄存器名称相近不表示 TX、RX 可以接反。

一次批量请求的过程是：外设发现 FIFO 满足阈值条件，拉高 REQ；DMA 按已经配置的 MSIZE 对应项数执行本次数据访问；最后一次面向外设的 AXI 数据传输完成后，DMA 拉高 ACK；外设看到 ACK 后拉低 REQ，DMA 随后拉低 ACK。外设确认 ACK 已撤销，才根据当时 FIFO 的情况决定是否发下一次请求。这里画的是动作顺序，不规定各动作间隔多少个时钟。

REQ 一旦发出，就必须保持到 ACK，即使 FIFO 数量已经不满足原来的阈值条件，也不能提前撤销。因此不能期待“FIFO 满了就把请求拉低”来修正过大的 MSIZE。反过来，即使阈值条件仍满足，也要先完成本轮请求和确认的撤销，再开始下一轮。

ACK 表示本次请求对应的数据访问完成，不表示整个 DMA 数据块结束，也不表示 TX 串行线路已经发送完成。AXI VALID/READY 则用于判断某个总线通道的一次传输是否被接收，两者不能混用。以下两张异常图假设本次不是块尾部；块尾部的单项请求在第 40 小节单独说明。

D 是外设 FIFO 深度，L 是已有条目数，B 是一次请求搬运的实际项数。

要确认什么 TX：DMA 写外设 RX：DMA 读外设

请求时至少保证 D−T 个空位 R+1 项有效数据

要点：TX：B ≤ D−T；RX：B ≤ R+1。先统一为“条目数”，再比较。

这里的 FIFO 是外设里的发送或接收缓冲区，不是 AXIDMA 通道内部的 FIFO。深度 D 表示最多能存多少个条目，L 表示当前已经存了多少个条目，空位数就是 D−L。后面的深度 16 是教学数值，实际配置必须读取外设能力或查当前实例配置，不能把 16 直接当成所有 示例平台 外设的深度。

阈值的含义要按具体外设核对。示例串行外设 的 T 是 SERIAL_DMA_TDL_REG 原值：TX 已有条目数 L≤T 时发请求。请求可能在 FIFO 更空时才被处理，但能保守保证的空位只有 D−T。例如 D=16、T=12 时，L=12 也已经满足条件，此时只有 4 个空位，不能按 FIFO 总容量 16 项配置一次写入量。

RX 的 R 是 SERIAL_DMA_RDL_REG 原值，触发条件是 L≥R+1。所以 R=3 表示至少有 4 项数据才请求，不是 3 项，也不是还剩 3 个空位。一次批量读取的 B 不应超过请求时能保证的 R+1。与 TX 不同，增加 RX FIFO 总深度，并不会改变同一个 R 所保证的数据数量。

B 始终表示 MSIZE 对应的实际项数，绝不是寄存器字段原值。本节假设一个 DMA 数据项对应一个外设 FIFO 条目。示例串行外设 封装采用 32-bit 数据寄存器访问，一个条目在 DMA 缓冲区占 4 B；串行线上有效数据有多少位是另一件事。还应保证 FIFO 由该 DMA 通道负责，CPU 和其他通道没有同时访问它，否则软件可能改变原本计算好的数量条件。

两条不等式用于保证一次请求的数量不超过外设可以提供的空间或数据。它们不保证 DMA 总能及时得到总线，也不取代尾部处理。其他外设若使用 L<T、L>R 或不同的阈值编码，必须先按手册换算，不能直接套用这里的加减关系。

36 · TX：只有 4 个空位，却要写 8 项

overflow（溢出）是向已满的 FIFO 继续写入数据；下面看第 5 项开始为什么没有空位。

16−12=4 个空位；前 4 项可以写入，继续写第 5～8 项有 overflow 风险。

假设：一项占一格；本次不是块尾部；期间外设未取走数据。示例串行外设 封装会拒绝此配置。

要点：改法一：B=4；改法二：保留 B=8，把 TX 阈值 T 调为 8 或更小。

先看左图：外设 TX FIFO 最多容纳 16 项，当前已有 12 项。因为 TX 阈值 T=12，L≤T 的条件已经满足，外设可以发出 DMA 请求。此时只有 4 个空位；FIFO 总深度是 16 并不表示还可以再写 16 项。

如果 DST_MSIZE 对应 8 项，DMA 会按本次批量请求尝试写入 8 项。假设期间串行发送没有释放新的空位，第 1～4 项写入后，FIFO 正好变为 16 项。到第 5 项时，FIFO 已满，第 5～8 项都没有可保证的存储位置。图中的中间八格是计划进行的八次写入，不是 FIFO 的额外容量。

这就是配置不匹配造成的 TX overflow 风险。若具体外设或总线接口支持满时阻止写入，现象也可能是等待或错误响应；若继续接受写入，则可能置溢出状态或丢失数据，准确行为应查该外设的手册和波形。不能依赖外围保护替代正确配置，也不能因为某次串行发送恰好释放了空位，就认为 B=8 总是安全。

有两种直接改法。第一种保持 T=12，把 B 改为 4，即 DST_MSIZE 字段编码改为 1；请求发出时至少有 4 个空位，正好够本次写入。第二种保留 B=8，即字段编码 2，把 T 调到 8 或更小，让外设等到至少有 8 个空位时再请求。第二种会让请求发得更晚，还要检查第 40 小节所说的 TX 响应延迟。

修正应从本次请求的数据项数和 FIFO 阈值入手。示例 serial_axidma_config_valid 已要求 burst_items≤tx_fifo_depth−tx_watermark，正常经过该封装的错误参数会在启动前被拒绝。本图用于说明校验原因，不是示例驱动发生的实测故障。

underflow（下溢）是从已空的 FIFO 继续读取；空位再多，也不能当作有效数据。

R+1=4 项有效数据；前 4 次可以读出，继续读第 5～8 项有 underflow 风险。

假设：一项占一格；本次不是块尾部；期间没有新数据到达。示例串行外设 封装会拒绝此配置。

要点：改法一：B=4；改法二：保留 B=8，把 RX 阈值原值 R 调为 7 或更大。

这次把方向换成 RX：外设收到的数据先进入接收 FIFO，DMA 再从数据寄存器读出并写到内存。深度仍为 16，R=3 表示已有 4 项时就满足 L≥R+1，可以发出批量请求。图中剩下的 12 个空位只是还能接收多少数据，与现在能读多少数据无关。

如果 SRC_MSIZE 对应 8 项，而这次请求期间没有新数据到达，那么前 4 次读取能取得有效数据；第 4 次之后 FIFO 已空。DMA 继续进行第 5～8 次读取，就是在访问没有有效数据的 FIFO，存在 underflow 风险。图中的第 5～8 个任务框用空心表示，不能把它们解释为四项合法的零数据。

空 FIFO 被读取后的实际结果由外设决定，可能置错误状态、返回无效值，或者通过总线接口等待新数据。总线访问成功返回也不自动证明数据有效，仍需查看外设状态和最终内容。如果串行输入恰好够快，错误参数可能暂时没有表现出来；配置应保证慢速或间歇输入时同样成立。

第一种改法是保留 R=3，把 B 改为 4，SRC_MSIZE 字段编码为 1。第二种改法是保留 B=8，字段编码为 2，把 R 调为 7 或更大，并保证 R 小于实际 FIFO 深度。R=7 时至少有 8 项才请求，够一次读取；但提高 RX 阈值会减少剩余空位，DMA 处理不及时时更容易发生接收溢出，需要一起检查服务延迟。

单独增加 FIFO 深度，不会改变 R=3 时只保证 4 项数据这一事实。示例串行外设 封装用 burst_items≤rx_watermark+1 拒绝这种数量不匹配。图中假设没有 CPU 或其他 DMA 通道抢先读走数据；若有并发访问，最初的数量条件可能不再成立。

或保持 B=8，把 R 改成 7		 前者分两次请求完成；后者等满 8 项
修改后都要逐项比较数据

要点：无 overflow、DMA DONE，都不代表数据正确。B 必须 ≤ 请求时保证的数据量。

本节把上一页的 RX 数据不足进一步展开为“DMA 完成，但内容错误”的反面教材。采用虚构 P2M 外设：RX FIFO 深度为 16，每条目 32 bit，每次读取数据端口取出一项。示例中的 11、22 等均为十六进制数据项的简写，例如 11 表示 0x00000011；每个格子对应 4 B，不是 1 B。源数据端口固定，目的内存地址递增，CPU 在 DMA 完成后正确同步目的缓存，排除缓存旧副本造成的误判。

关键前提：这个反例假设空 FIFO 的数据寄存器仍接受读访问、返回 0，且不给出总线错误；外设错误状态不阻止本次请求。一笔批量握手已经授权 DMA 读取 B 项，期间不会按 FIFO 非空状态逐项阻止后续访问。这些是虚构外设的特定行为，不是 AXIDMA 对所有外设的保证。有些外设会等待新数据或返回错误，就不会表现为本例的零填入。

错误配置为 R=3，即 L≥4 时发批量请求；SRC_MSIZE 字段写 2，对应 B=8。传输总量设为 8 个源项，因此 BLOCK_TS=7。它不是“剩余量小于 MSIZE”的尾部单项处理场景，而是完整的一次 8 项请求。示例驱动的正常参数校验原本会拒绝 B>R+1；本节假设绕过这层校验直接写寄存器，用于说明校验不可省略，不建议在实际环境直接执行。

外设先接收 11、22、33、44 四项，然后暂停输入，直至这一批 DMA 访问结束。FIFO 有 4 项就触发请求。前四次数据端口读取得到这四项，后四次面对空 FIFO，按本例的接口约定返回 0。DMA 将八个返回值共 32 B 写入目的区，所有总线访问均正常完成，因此可以报告 DMA DONE。底层原因仍是从空 FIFO 读取，即 underflow（下溢）；本节强调的是它可能表现成数据错误，而不是显式的 DMA 错误。没有 overflow 不等于没有其他 FIFO 使用错误。

之后另外四项 55、66、77、88 才到达。DMA 已完成预定的八项，后四项留在外设 FIFO 中，没有进入本次目的缓冲区。整个过程 FIFO 最多只有四项，远未达到深度 16，因此不发生接收溢出。不要把这些残留直接交给下一笔任务，否则还可能产生下一次接收数据错位。

修改方法一：R=3 不变，SRC_MSIZE 字段写 1，对应 B=4；第一批读取四项，第二批到达后再读取四项，整块仍为八项。修改方法二：B=8 不变，R 改为 7，使外设积累八项后再请求。后者等待更久、剩余 FIFO 空间更少，仍需评估输入速率和 DMA 服务延迟。停止通道并按外设规定恢复 FIFO 状态后再改配置，不能在活动请求中途修改。

验证应使用预期值已知且非零的序列，比较全部八项，检查外设数据端口的实际读取次数及读取时的 FIFO 数量，再看 DMA 完成和总线响应。不要把一次握手等同于一笔 AXI burst；本例按外设条目计数，具体总线访问可能经过拆分。M2P 应对应检查目的端 DST_MSIZE 与可保证空位，本节不把 P2M 的空读结果套用到 M2P。

确认单位和阈值 → 算可保证数量 → 选合法项数 → 转成字段编码。下表均为深度 16。

要点：示例串行外设 共用 burst_items：B ≤ min(D_TX−T, R+1)，两侧都要满足。

实际配置按四步进行。第一步确认 TX/RX 的实际 FIFO 深度、条目宽度、阈值比较方式和谁负责访问 FIFO。示例串行外设 通过 capability.tx_fifo_depth、capability.rx_fifo_depth 保存能力信息；本节的 16 只是算例。先将 DMA 数据项与外设 FIFO 条目统一，再计算。

第二步计算能保证的数量。TX 是 D_TX−T 个空位，RX 是 R+1 项数据，同时要求 0≤T<D_TX、0≤R<D_RX。若接口允许分别设置，TX 和 RX 分别计算 B_TX 与 B_RX。示例 serial_axidma_config_t 只有一个 burst_items，并用于两边，所以它必须小于等于两侧结果中的较小值。

第三步选当前实例和接口支持的项数。示例串行外设 封装接受 1、4、8、16、32 项；应在不超过上述限制的值中选择。例如 TX、RX 都只保证 6 项，不能填 6，也不能向上选 8，可以从 4 项开始。满足数量关系的最大合法项数是一个可测试的起点，不等于所有负载下最好的性能配置。

第四步区分接口参数和寄存器编码。burst_items 填实际项数，封装函数 serial_axidma_msize 负责转换；4 项对应字段编码 1，8 项对应编码 2。直接配置 CHx_CTL 时使用对应枚举或编码，不要把数字 4 直接写进 MSIZE 字段来表示四项，因为字段值 4 代表 32 项。也不要把字段编码 2 传给只接受项数的 burst_items。

以两侧深度都为 16、T=12、R=3 为例：应用填 tx_watermark=12、rx_watermark=3、burst_items=4；驱动写入阈值寄存器原值，并将四项转换为 MSIZE 编码 1。配置应在驱动规定的停用状态下更新，不能在一次握手中途修改。若希望每次搬 8 项，可以先试 T=8、R=7、burst_items=8，再验证延迟和尾部。

最后一个不对称例子也很重要：T=8、R=3 时，TX 本来能支持 8 项，但 RX 只保证 4 项。当前共用参数只能选 4；若一定要用 8，应先调整 RX 阈值并重新评估服务延迟。示例驱动在 serial_axidma_config_valid 中检查这些限制，不满足时 open 返回错误，不会继续启动 DMA。

40 · 数量匹配以后，还要检查延迟和尾部

两条不等式解决一次请求能否搬完；持续传输和最后几项还需要单独检查。

TX：请求会不会太晚

  • T 越小，允许的批量越大
  • 但请求时剩余数据更少
  • DMA 太慢，发送可能断流

RX：请求会不会太晚

  • R 越大，请求时已有数据越多
  • 但剩余空位更少
  • DMA 太慢，接收可能溢出

尾部：10 项，B=8，R=7

  • 先搬 8 项，最后剩 2 项
  • 单项握手正常时按 8+1+1 完成
  • 检查 dma_rx_single 的连接

验证：把数量与波形对应

  • 看 FIFO 数量、REQ / ACK / single
  • 统计数据端口实际读写次数
  • 检查错误、完成和数据内容

要点：先保证每次有足够空间或数据，再验证最慢响应、尾部请求和最终内容。

前两张错误图讲的是“这一次要求搬得太多”：TX 空位不足却继续写，存在 overflow 风险；RX 数据不足却继续读，存在 underflow 风险。还有另一类问题：每次数量都合理，但 DMA 迟迟没有服务。此时 TX 可能因无数据可发而断流，RX 则可能因新数据持续到达而溢出。不要混淆两类原因。

TX 降低 T，可以保证更多空位，也允许更大的 B，但发请求时 FIFO 里的剩余数据更少。它必须能支持 DMA 等待仲裁、经过互连并开始补充数据所需的时间。RX 提高 R 可以积累更多有效数据，却只剩 D_RX−(R+1) 个空位来接收后续数据。阈值选择既要考虑一次请求的数量，也要给最慢响应留出余量。

如果速率近似稳定，可以先估算：TX 在 L=T 时的剩余发送时间约为 T÷发送条目速率；RX 在 L=R+1 时的剩余接收空间时间约为 [D_RX−(R+1)]÷接收条目速率。它们是从触发阈值到空/满的大致时间，不包含所有突发、相位和启动影响。应让实际 DMA 服务延迟明显小于相应时间，并验证长期平均搬运速度足够；算式成立不代表持续压力一定通过。

尾部以总量 10 项、B=8、R=7 为例：第一次有 8 项时产生批量请求并读出 8 项，最后到达的 2 项低于批量阈值，不会再产生同样的批量请求。串行外设 手册规定，RX FIFO 至少有一项时可以通过 dma_rx_single 表示可读。DMA 控制块长度时，剩余量小于 MSIZE 后进入单项处理阶段；若单项信号连接和配置正确，就能按 8+1+1 完成。相同位宽下，总 10 项的 CHx_BLOCK_TS 字段为 9。

因此，“低于批量阈值”不等于必然卡住，要确认该外设和芯片确实接入了单项握手。如果尾部没有继续搬运，检查 DMA 剩余量、dma_rx_single、握手选择和 FIFO 现存条目。单纯延长 timeout 不会产生缺失的请求；把 B 改小也不能自动改变阈值条件。对未支持单项请求的外设，必须按该外设支持的方式安排尾部，不能随意套用本例。

建议验证整批和带尾部两类长度，再加入总线竞争或输入停顿。观察外设 FIFO 条目数、dma_req、dma_ack、dma_single，以及数据寄存器端口成功读写的次数；若经过总线桥，应在外设端口核对条目，不能只数 DMA 侧 AXI 地址请求。最后检查 DMA/外设错误状态、最终完成和数据内容。当前材料没有执行硬件实验，本节描述的是验证方法。

九、完成、中断与缓存一致性

41 · 先分清三个“完成”

一块结束、整次 DMA 结束、CPU 收到通知，含义不同。

BLOCK_TFR_DONE

  • 某一个块完成
  • LLI 中可能还有后续描述符

DMA_TFR_DONE

  • 整次 DMA 传输完成
  • 用来判断有限链或单块的最终结果

IRQ / callback

  • 软件收到事件通知
  • 是否产生还受多级使能和路由控制

INTSTATUS 与 INTCLEAR

  • 先保存状态，区分完成和错误
  • 再向对应位写 1 清除已处理事件

要点：CPU 收到中断之后，仍要读取原因、检查错误并同步目的缓存。

块完成事件描述当前块的进度；整次 DMA 完成事件描述整个任务的结束。在多描述符传输中，第一块完成时不能立即复用整条链涉及的缓冲区。IOC_BlkTfr 决定是否报告相应块事件，最终完成另有判断。

中断是通知方法，不是第三种数据搬运机制。状态记录、通道信号输出、控制器全局使能、平台中断路由和 CPU 中断状态都会影响能否进入 ISR。轮询关闭信号输出时，状态仍然可以正确记录。

ISR 是中断处理函数。它应先读取并保存原因，清除已经处理的外设事件，再通知上层。对高电平中断，如果根因没有解除，中断可能持续触发；反复进入 ISR 不代表发生了多次独立传输。

软件要同时看最终完成和错误位，不能发现一个 DONE 就忽略其他错误。成功后还需执行目的缓存同步并检查数据；错误和超时则保存现场，确认硬件停止后再清理。第 47 小节的用例用于检查状态与信号使能的区别。

42 · 有完成状态，却没有进入预期回调

按通知经过的顺序检查，不要只盯着 DMA 的一个状态位。

  1. DMA 事件：检查 INTSTATUS、INTSTATUS_ENA、INTSIGNAL_ENA 和全局中断使能。
  2. 中断控制器：检查中断源使能、待处理状态，以及路由到哪个 CPU。
  3. CPU 接收：检查 CPU 中断使能、入口映射和实际收到的中断编号。
  4. 处理函数：确认函数签名、上下文有效期、状态清除和回调条件。

要点：中断源编号与 CPU 入口编号需要按映射关系核对。

本教学平台假设 DMA 使用中断源 12，经中断控制器映射到 CPU 入口 40。这两个编号属于不同位置，不能直接比较；应查映射表确认对应关系。编号仅用于本例。

先检查 DMA 是否记录事件，再检查是否允许输出通知。之后沿中断控制器和 CPU 入口逐级检查使能、待处理状态与路由。一次转发可能使上一级待处理状态清除，不应要求所有位置同时保持待处理。

处理函数的参数必须与注册接口一致。设备上下文必须在注册期间保持有效，不能通过强制类型转换掩盖函数签名不匹配。

处理函数读取并记录事件，按寄存器规则清除状态，然后调用上层回调。多个通道共用控制器时，初始化、释放和中断分发需要统一协调，避免一个使用方关闭另一个仍在工作的资源。

43 · CPU 与 DMA：为什么需要同步缓存？

教学前提：DMA 与 CPU 缓存不自动保持一致。

要点：CPU 写完不代表内存已更新；DMA 完成不代表 CPU 缓存已更新。

先看上半部模型。CPU 经数据缓存访问内存，DMA 作为另一个总线访问方，经同一片互连读写内存。DMA 不在 CPU 到内存的必经路径上。这里假设缓冲区可缓存，CPU 使用写回缓存，而且 DMA 与 CPU 缓存不自动保持一致；具备硬件一致性的平台应按其自身接口约定处理。

图中两个例子是独立情境。左例中，CPU 把源数据从 A 改成 B，新值暂留在缓存里，内存还是 A。DMA 直接读取内存，因此会读到 A。启动前对源区执行 clean，将修改写回到 DMA 可见的位置，才能保证 DMA 读到 B。

右例中，DMA 已把目的内存写成 C，但 CPU 缓存仍保存 A。CPU 若命中旧缓存，读到的仍是 A。确认 DMA 完成后，对目的区执行 invalidate，使旧副本失效；CPU 随后重新读取，才能取得 C。完成状态正确和 CPU 看到新数据是两个不同检查点。

clean 表示把缓存中的修改写回内存，invalidate 表示使缓存副本失效。示例 BSP 的 sync_for_device 对指定区域执行写回并失效，sync_for_cpu 在 DMA 完成后使目的区域的旧副本失效。操作范围还要考虑缓存行对齐；缓存行是硬件维护缓存的基本块。

源区域需要启动前写回，否则 DMA 可能读到内存中的旧内容。目的区域也要在启动前处理，避免 CPU 缓存里的旧修改在稍后写回，覆盖 DMA 的新结果。传输期间 CPU 应让出这段缓冲区的使用权。

即使本次启动前已经失效目的缓存，结束后的同步仍属于驱动契约。其他访问或平台行为可能使缓存重新产生副本，不能因为几次测试“省略后也通过”就取消这一步。

fence 约束顺序但不负责写回脏数据；volatile 不能保证 CPU 与 DMA 一致；地址别名转换也不能替代缓存维护。ARCACHE/AWCACHE 描述 AXI 访问属性，配置成某个值并不会自动建立 CPU 与 DMA 的硬件一致性。

本教学例为简化所有权管理，DMA 运行期间 CPU 不访问这次传输的源、目的缓冲区。目的区的旧脏缓存必须在 DMA 启动前按平台接口处理，不能等 DMA 写完后再将旧内容 clean 回去，否则可能覆盖新结果。还要维护所需缓存层级并完成平台要求的同步屏障；不要仅对着示意图自行省略 DMA 同步接口。

44 · 一行 fence，分清编译器与 CPU 的职责

这行内联汇编同时涉及两层顺序约束；它不是缓存刷新指令。

fence rw, rw

  • CPU 执行的指令
  • 约束前后内存读写
  • 被外部观察到的顺序
  • 不自动 clean 缓存

“memory”

  • 给编译器的声明
  • 限制相关内存访问
  • 跨越此处重排
  • 自身不产生硬件屏障

volatile

  • 给编译器的限定
  • 防止将汇编当作
  • 无用代码删除
  • 单独使用不保证访存顺序

要点：fence 管硬件访存顺序；memory 管编译器重排；volatile 保留汇编。缓存维护另做。

先把这一行分为 CPU 执行的指令和给编译器的说明。引号中的 fence rw, rw 会成为机器指令；volatile 和 memory 属于内联汇编语法，不是传给 DMA 的配置。

fence rw, rw 中，逗号前的 rw 表示前面的普通内存读写，逗号后的 rw 表示后面的普通内存读写。CPU 必须满足这些访问的可观察顺序约束。它不是要求所有指令都按序执行，也不是把所有数据自动写到内存；即使处理器按序执行，写缓冲等机制仍可能影响外部看到的访问顺序。

最后的 memory 告诉编译器，这段汇编可能访问未通过输入输出参数逐项声明的内存。编译器需要据此约束相关内存访问重排并重新考虑已缓存的内存值。这个声明本身不会生成 CPU 内存屏障，也不会刷新硬件缓存。

volatile 表示这段汇编有不能随意丢弃的作用，避免被当作无用代码删除；它本身不是通用编译器内存屏障，不保证所有其他语句都不能移动。不要与 C 变量的 volatile 混为一谈。

描述符场景需要分别解决：编译器正确安排访问；缓存维护使新内容对 DMA 可见；平台所需的屏障保证准备操作与启动操作的顺序。顺序屏障不能替代 cache clean，cache clean 也不能脱离平台约定独立推导所有顺序保证。

本节逐项解释这一行，不把它当作所有平台的完整 DMA 启动屏障。RISC-V 的 rw 覆盖普通内存读写，设备 I/O 另有 i/o 类别。普通内存写与 MMIO 启动寄存器写之间，需要结合平台属性、缓存维护及 MMIO 接口的保证，选用含相应 I/O 顺序的屏障；不能仅凭 fence rw,rw 就宣称完整覆盖。

45 · 教学案例：DMA 完成，目的数据却没变

教学情境：CPU 预检查通过，DMA 完成后却读到目的区旧值。

看到的现象

  • 256 B 教学搬运，未报告 DMA 错误
  • CPU 却读到目的区旧模式

检查到的原因

  • 示例同步函数只有编译器屏障
  • 没有真正执行数据缓存维护

修正后的方法

  • 启动前处理源、目的缓存
  • 完成后处理目的缓存，再做比较

这个案例的启发

  • CPU 预检查不能代替 DMA 可见性检查
  • 小缓冲区还要排除共享缓存行影响

要点：先核实缓存维护是否真正执行，再根据总线证据判断搬运是否异常。

假设 CPU 可以正常写读 SRAM，DMA 没有报告错误，但完成后 CPU 比较数据仍读到旧模式。这些现象不能单独证明 DMA 没有写数据，缓存可能改变 CPU 看到的结果。

在这个教学案例中，同步函数只有编译器屏障，没有真正执行缓存写回或失效。编译器屏障不能代替数据缓存维护。应按平台要求实现缓存操作，再观察总线与内存结果。

源、目的区域距离太近时可能共享缓存行。本例约定缓存行 64 B，缓冲区按缓存行对齐并隔离，避免同步一段区域时同时影响相邻数据。

若正确同步后仍失败，继续检查源数据、写字节使能、目标地址与保护区域。本案例用于说明排查方法，不表示所有数据错误都由缓存引起。

十、测试设计与问题定位

46 · 测试目录与通过结果，分别说明什么

有用例入口、执行通过与覆盖完整，是三件不同的事。

范围 示例检查内容 不能直接推导什么
单块 / LLI 小规模数据搬运、位宽与完成路径 全部长度边界和参数组合通过
多通道 / 优先级 多个通道启动、配置与数据检查 仲裁顺序或持续带宽已验证
中断 / 复位 通知开关、复位后重新工作 全部错误注入和在途复位通过
外设 DMA 串行外设的发送、接收与握手 长时间压力与所有阈值均已覆盖
专项验收 4 KiB 边界、内存压力、主动停止 不能用普通清理流程或 PASS 替代

要点：批量运行只执行已注册用例；PASS 的范围取决于实际检查项。

假设教学测试目录注册了单块、LLI、中断和复位四项。批量命令只调用这四项，不自动包含边界、性能或外设测试。用例目录与完整测试设计应分别维护。

存在入口只说明能够启动一段测试代码。是否执行过、在什么环境通过，以及检查过哪些条件，需要单独记录。通过数量不能直接当作功能覆盖率。

批量运行可以在子项失败后继续执行，但必须保留每项结果和总失败数。应检查失败明细，不能只取中间一行 PASS。

本节描述教学测试设计，没有声称执行过硬件回归。实际运行时还需记录软件版本、平台配置、参数与判定条件。

47 · 用三个教学用例理解检查目标

把每个用例的动作与结论对应起来，避免扩大 PASS 的含义。

用例 具体动作 通过能说明什么
四通道 M2M CH1～4 各 512 B；不同数据模式；先启动再逐一等待 这些缓冲区的数据传输正确
中断开关 先关 signal 等完成，再开 signal 检查 callback 与数据 状态记录和中断通知按配置工作
复位工作循环 20 轮：空闲时复位、检查复位态、执行新一轮搬运 复位后可以重复恢复基本传输

要点：测试证明的是它实际检查过的条件。

四通道测试给 CH1～CH4 分配不同缓冲区和数据模式，每通道搬 512 B。代码先逐个启动通道，再逐通道等待和比较。这样能产生多个通道工作重叠的机会，但不是同一时钟沿原子启动，更不是四个 CPU 核各自管理通道。

direct 中断测试分两阶段：状态记录开启而信号输出关闭时，应能轮询完成且 callback 计数为零；打开信号后，再检查 callback 的通道、状态以及搬运数据。这个设计能够验证两个使能层次，不只是“中断函数打印过一行”。

复位用例执行 20 轮，复位发生在新一轮搬运之前，检查 DMAC_CFG、CHEN 等复位态，再运行 256 B 搬运并变化数据模式。它验证的是反复复位后的恢复能力，不是传输正在进行时的复位行为。

类似地，优先级用例交换 CH1/CH2 优先级，并检查读回、完成和数据，但没有记录竞争时的授权顺序。数据 PASS 不足以证明仲裁确实优先服务了高优先级通道。

48 · 教学案例：LLI 数据正确，状态却没有写回

本教学配置未启用描述符状态写回，内存中的完成位不会自动更新。

原先的期望

  • DMA 执行 LLI 后
  • 描述符 LLP_STATUS 完成位被写回

实际观察

  • 业务数据和最终完成可以正常
  • 状态区域仍保持初始化值

示例配置

  • 本教学实例未启用状态写回
  • 延长等待不能使完成位更新

当前应验证

  • IOC=0 的块事件行为、最终完成
  • 数据正确、通道结束及后续复用

要点：验收条件必须符合当前实例配置，不能只依据手册列出的可选能力。

假设测试希望检查描述符 LLP_STATUS 中的完成位，但本教学配置明确未启用描述符状态写回。这些位置保持初始化值是本配置下的预期行为。

通道 INTSTATUS 是 DMA 状态寄存器，描述符 LLP_STATUS 是内存中的可选写回区域。前者出现完成，不代表后者一定改变；后者未改变，也不自动表示业务搬运失败。

验收应检查符合配置的事件行为、最终完成、数据正确和通道退出。对于本例未启用的写回能力，应记录为不适用，不能延长等待后把结果改称写回通过。

若另一种教学配置启用写回，则需补充状态地址、缓存同步、更新内容和时序检查。通用功能说明与具体实例配置应分别阅读。

49 · 传输异常时，按现象选择下一步

先保存同一次传输的配置和状态，再通过波形缩小问题范围。

现象 先检查 需要的证据
没有任何访问 时钟、复位、DMAC_EN、CHEN / WE、模式 配置读回与 AR / AW 是否出现
读请求有，数据不返回 地址路由、目标响应、RREADY ARADDR / ID、RVALID / RESP
能读，但写不动 AW / W 接收、FIFO 条件、B 响应 AWREADY、WREADY、BVALID / RESP
完成但数据不对 总量、位宽、WSTRB、地址与缓存 首错偏移、总线数据、缓存同步
LLI 后续块不动 LLP、对齐、VALID、LAST、描述符同步 描述符内容和对应地址的读取

要点：每一步都回答：有没有发请求、有没有返回、有没有写对、CPU 有没有看到。

第一步保存地址、长度、位宽、MSIZE、LEN、CFG、CTL、CHEN、INTSTATUS，以及软件等待结果。若在错误路径里先复位再打印，就可能丢失最有用的证据。日志中的“没有中断”也要区分未产生事件和回调没有被执行。

没有 AR/AW 时，先查启动是否被硬件接受；外设模式还要查握手。请求已经被接收却没有返回时，再看目标和返回通道。数据返回后写侧停住，要分别看地址、数据和响应，不要把三种等待合成一个“总线卡住”。

完成但比较失败时，记录第一个错误字节及前后数据。整体未变优先核对地址和缓存；周期性错位应检查 SIZE、字节位置和结构布局；只错最后几项应检查 BLOCK_TS、尾包与阈值。这些是排查顺序，不是凭现象直接确定根因。

超时后先确认停止，再复用缓冲区或做下一次测试。尝试修改参数时一次改变一个因素，并保留修改前后的相同证据，才能判断哪个条件真正影响了结果。

50 · 怎样设计一组更有说服力的验证

围绕边界和可观察结果设计用例，分别记录功能、协议和性能结论。

功能结果

  • 源、目的有效数据一致
  • 保护区未改变，错误状态为零

数量边界

  • 1 项、整 burst、带尾部、跨 4 KiB
  • 源、目的位宽与边界分别变化

协议行为

  • 握手拍数符合实际 LEN
  • LAST、RESP、WSTRB 与地址一致

压力与性能

  • 多轮、多通道、延迟与停止场景
  • 计时范围明确，再报告带宽

要点：保留固件 / 硬件版本、命令、配置、原始日志和对应波形。

验证应围绕明确问题设计。例如检查 ARLEN 是否按预期工作，就记录实际 AR 请求字段和对应的数据握手数量；只比较最终内存内容不能证明请求没有被拆分。检查优先级则需要两个通道形成真实竞争，并记录授权或进度。

长度可选择一项、恰好一笔、比一笔多一项和跨 4 KiB 等代表值。位宽和地址组合必须先满足当前实例能力，再做受约束的组合覆盖。不要为增加测试数量而生成大量非法或重复场景。

正常完成、错误响应、软件等待超时、主动停止和复位分别需要自己的通过条件。普通 close/cleanup 存在，不等于主动停止不丢数据已经验证；空闲时复位成功，也不能替代在途复位。

建议结果记录至少包含：测试目的、版本、命令、缓冲区、配置、期望、实际状态与数据、波形位置、结论及限制。历史 PASS 只能证明当时被检查的范围；固件或硬件配置变化后，应重新验证相关部分。

十一、回顾与讨论

51 · 把一次 DMA 做对，记住这四步

地址与数量正确，是开始；CPU 最后读到正确数据，才完成软件验收。

配置前

  • 确认资源、地址、位宽和总量
  • 分清 BLOCK_TS、MSIZE 与 AxLEN

启动前

  • 准备缓冲区与描述符，同步缓存
  • 配置完成后再设置 CHEN / WE

完成后

  • 检查最终完成与错误
  • 同步目的缓存，比较数据和边界

出错时

  • 保存状态，按读写路径检查波形
  • 确认停止后再复用资源

要点：讨论：面对一笔异常传输，你会先保存哪几个寄存器、抓哪组信号？

回到第 5 小节的 M2M 路径：CPU 提供任务，DMA 经互连读取源数据，暂存在通道 FIFO，再写入目的区域，最后通过状态或中断报告结果。理解这条路径，参数、代码和波形就可以对应起来。

M2M 中，BLOCK_TS 规定整块的源数据项数；MSIZE 参与源、目的内部请求的数据量组织；配置 AxLEN 指定希望采用的长度，实际总线 AxLEN+1 才是本笔确定的拍数。FIFO 容量、剩余数据和地址边界也会影响实际长度。仅凭 MSIZE 和配置 LEN，不能确定每笔实际拍数；应结合总线请求与有效数据量检查结果。

单块方式适合先把基础流程验证清楚；LLI 用于预先组织多段搬运，但描述符本身同样需要正确地址、布局、有效位和缓存同步。当前实例未启用的能力，不能作为必需验收条件。

可以用三个问题组织讨论：40 项、MSIZE 对应 16 项、期望 8 拍时，三个字段分别填什么？为什么仅看配置 LEN 无法知道最终每笔拍数？LLI 数据正确但内存状态位为零，应先检查什么？答案分别见第 14、13～16 和 48 页。
