从枚举到交互：SoC PCIe RC 与 EP 的完整软件实战流程

教程

简介

本文从软件视角系统梳理 PCIe 在 Linux 场景下的完整工作流。

PCIe 设备在系统中通常扮演两种角色：

  • RC，Root Complex，根复合体
  • EP，Endpoint，端点设备

两者职责完全不同，软件栈也完全不同。

如果只看协议，很容易把 PCIe 理解成“高速总线”；但如果站在系统软件角度，它其实是一整套“发现设备、分配资源、建立地址映射、完成中断和 DMA 交互”的机制。

本文采用一个非常典型的工程场景来讲：

  • 主机：x86 服务器，充当 RC
  • 设备：AI 加速卡，板上 SoC 内部集成 PCIe EP 控制器

围绕这个场景，我们重点回答下面几个问题：

  1. 服务器上电后，RC 是如何发现这张 AI 卡的？
  2. RC 是如何给 EP 分配 BAR、配置内存窗口和总线号的？
  3. Linux 内核接管后，为什么还要重新枚举一遍？
  4. RC 如何通过 BAR 访问 EP 的寄存器和片上内存？
  5. EP 又是如何反向访问 RC 侧内存的？
  6. 中断、DMA、MSI 在这个过程中分别扮演什么角色？

本文的目标不是只讲某一个寄存器，而是把从冷启动到双向数据交互之间的整个软件流程串起来。

一、先建立整体图景

在服务器 + AI 加速卡这个场景下，PCIe 软件流程大致可以分成 5 个阶段：

  1. 硬件冷启动，PHY 上电，链路训练
  2. BIOS/UEFI 枚举 PCIe 拓扑，给设备分配资源
  3. Linux 内核重新扫描总线，重建自己的 PCIe 视图
  4. 主机侧 PCI 功能驱动和 EP 固件/驱动分别完成各自初始化
  5. 双方通过 BAR、DMA、MSI 建立正常的数据通路

可以把它理解成一句话：

先把链路打通，再把设备找出来；先把地址和中断配好，再谈寄存器访问和 DMA 传输。

二、RC 和 EP 的本质区别

1. RC 是 PCIe 树的根

RC 是整个 PCIe 域的发起者和管理者。

它的职责包括：

  • 提供配置事务的发起能力
  • 发起总线枚举
  • 给下游设备分配 Bus Number、BAR 地址、中断资源
  • 作为 CPU 和内存系统与 PCIe 拓扑之间的桥梁

从软件上看，RC 不是“一个普通 PCIe 设备”，而是整棵 PCIe 树的入口。

2. EP 是被发现、被配置、被访问的一方

EP 是挂在 PCIe 树下游的功能设备，比如：

  • AI 加速卡
  • SSD
  • 网卡
  • 采集卡

EP 本身不会主动枚举自己，也不会给自己分配 BAR 地址。它负责做的是：

  • 按 PCIe 规范提供配置空间
  • 上报自己支持哪些 BAR、MSI/MSI-X、Capabilities
  • 响应 RC 发起的配置和内存事务
  • 在被驱动初始化后执行真正的数据处理工作

所以 RC 和 EP 的一个核心差异是：

  • RC 管理系统资源
  • EP 消费系统资源并提供功能

三、硬件冷启动阶段到底发生了什么

在软件真正开始运行之前，PCIe 已经先完成了一部分纯硬件事务。

1. 供电、时钟、复位

主机上电后，主板和卡槽先完成：

  • 电源稳定
  • 参考时钟输出
  • PERST# 复位控制

对 AI 加速卡来说，这一步的意义是：

  • EP 控制器和 PHY 进入已知状态
  • 外部参考时钟稳定
  • 等待 RC 释放复位

2. 链路训练由硬件自动完成

一旦 PERST# 释放，RC 和 EP 的 LTSSM 就开始工作。

这一步本质是双方 PHY 和链路层硬件在协商：

  • 对端是否存在
  • 支持多少 lane
  • 当前可以工作在哪个速率
  • 是否能进入 L0 正常工作态

这一步还没有 Linux，没有驱动，甚至 BIOS 代码都未必已经开始全面接管。

所以一定要记住：

PCIe 软件建立在“链路已经训练成功”这个前提上。

如果链路都起不来，后面所有枚举、BAR、DMA 都无从谈起。

四、BIOS/UEFI 阶段：第一次枚举是谁在做

很多人第一次接触 PCIe 时会有一个误区：以为 Linux 是第一个发现 PCIe 设备的。

实际上，绝大多数 PC/服务器平台上，最早做 PCIe 枚举的是 BIOS/UEFI。

1. BIOS 在 RC 侧的主要工作

BIOS 需要完成整个 PCIe 拓扑的初始构建。

它会做这些事：

  • 从 Root Port 开始向下扫描设备
  • 读取每个设备的 Vendor ID / Device ID
  • 判断当前设备是普通 EP 还是桥设备
  • 给桥设备分配 Secondary/Subordinate Bus Number
  • 读取 BAR 大小需求并为其分配地址空间
  • 根据设备能力识别 MSI/MSI-X 等扩展能力

这一步做完后，BIOS 才能知道：

  • 这台机器上到底插了哪些卡
  • 每张卡各自占用了哪些 MMIO 地址
  • 哪些设备具备启动阶段必须的功能

2. BAR 分配的本质

BAR 的本质是“把设备资源映射进系统地址空间的窗口”。

对 AI 加速卡来说，常见会有几类 BAR：

  • BAR0：控制寄存器窗口
  • BAR2/BAR4：片上 SRAM 或 doorbell 窗口
  • 某些设备还可能映射大块 DDR 或片上内存窗口

BIOS 通过“写全 1 再回读”的方式探测 BAR 大小，然后在系统物理地址空间中给它们分配一个不冲突的范围。

之后：

  • RC 侧 CPU 访问这段物理地址
  • 实际上就是访问 EP 暴露出来的资源

3. BIOS 对 EP 做了什么

从 EP 的角度看，BIOS 做的是：

  • 发现我
  • 识别我
  • 给我的 BAR 分配地址
  • 使能我的配置和内存响应

BIOS 不一定会完成设备业务初始化，但至少会把设备放到“可以被操作系统继续接管”的状态。

五、Linux 为什么还要再枚举一次

这一步是很多工程新人最容易疑惑的地方。

既然 BIOS 已经枚举过了，Linux 为什么不直接用？

答案是：因为 Linux 要建立自己的设备视图和管理状态，而不是简单把 BIOS 的结果当成唯一事实来源。

1. 内核需要自己的资源视图

在本文讨论的 x86 服务器场景里，Linux 启动后主要会解析 ACPI/MCFG 这类平台信息，知道：

  • PCIe 配置空间如何访问
  • Root Complex / Root Port 相关资源如何暴露
  • MCFG 等配置空间信息如何映射

但 Linux 仍然会重新扫描 PCIe 总线，并建立自己维护的 pci_bus / pci_dev 视图。

在大多数常见 PC/服务器平台上，Linux 的主路径是：

  • 重新扫描总线
  • 重新构建自己的设备树
  • 重新读取并确认 BAR、桥窗口、中断能力等信息

这里要特别区分两件事：

  • 重新枚举设备：这是 Linux 的常规行为
  • 重新分配 BAR/桥窗口资源：这并不是所有平台上的默认主路径，很多时候 Linux 会沿用固件已经建立好的资源布局，只在特定条件下才调整或重分配

原因很简单：

  • BIOS 的目标是把系统带起来
  • Linux 的目标是长期、统一、可管理地运行整个系统

2. Linux 中的枚举过程

Linux 的 PCI 子系统会从根总线开始递归扫描。

它做的事情包括：

  • 为每个设备创建 struct pci_dev
  • 解析其配置空间和 capability 链
  • 识别普通设备、桥设备、热插拔能力、MSI/MSI-X 能力
  • 建立 /sys/bus/pci/devices/ 下的设备视图

这一阶段之后，lspci、setpci、sysfs 这些工具才能看到完整设备信息。

3. 从“设备存在”到“驱动可用”还有一步

被枚举出来，只代表：

  • 系统知道这张卡存在
  • 知道它的资源窗口和配置能力

但这并不代表设备已经能工作。

真正让它工作的是后面的驱动 probe()。

六、主机侧 PCI 功能驱动在 Linux 下到底做了哪些事

这里需要区分两个概念：

  • RC 控制器驱动：负责 host bridge / root port/controller 本身
  • 主机侧 PCI 功能驱动：绑定到枚举出来的 AI 加速卡这个 pci_dev

本节讨论的是后者，也就是 Linux 如何把“这张被枚举出来的 PCIe 卡”变成“内核里可用的功能模块”。

1. 资源申请和寄存器映射

驱动首先会做两件事：

  • pci_request_regions() 之类的资源申请
  • pci_iomap() / pcim_iomap() 之类的 BAR 映射

这意味着：

  • BAR 对应的物理地址范围被正式声明占用
  • 驱动拿到了访问设备寄存器的虚拟地址

从此以后，驱动对设备寄存器的访问，本质就是对 BAR 窗口的一次 MMIO 读写。

2. 开启 Bus Master

这是主机侧 PCI 功能驱动最关键的一步之一。

通过 pci_set_master()，驱动会打开设备的 Bus Master 能力。

不打开它的后果是：

  • 设备不能主动发起 DMA
  • 即使 BAR、寄存器、中断都配好了，真正的大数据传输仍然跑不起来

所以工程里经常把它视为“DMA 通路开关”。

3. 中断初始化

现代 PCIe 设备通常优先使用 MSI/MSI-X，而不是老式 INTx。

驱动会完成：

  • 申请 MSI/MSI-X vector
  • 注册中断处理函数
  • 配置设备内部中断使能寄存器

一旦设备完成 DMA、队列处理或异常上报，就可以通过 MSI 通知 RC 侧 CPU。

4. DMA 能力和地址位宽配置

驱动还要配置 DMA 掩码，例如：

  • 32-bit DMA
  • 64-bit DMA

这一步实际上是在告诉内核和设备：

  • 设备最多能访问到多高位的物理地址
  • 后续 DMA buffer 该如何分配

如果这一步配错，很容易出现：

  • DMA 能跑，但偶发读写异常
  • 某些大内存机器上才复现的问题

七、EP 侧软件到底负责什么

在服务器 + AI 加速卡的场景里，EP 侧的软件往往不是 Linux 主机驱动，而是卡上的固件、RTOS、裸机程序，或者板载 SoC 上的 Linux 驱动。

EP 的工作重点和 RC 完全不同。

1. 提前准备好“给 RC 看见”的内容

EP 需要准备的通常包括：

  • 配置空间内容
  • Vendor ID / Device ID / Class Code
  • BAR 属性和大小
  • MSI/MSI-X 支持能力
  • inbound/outbound 地址窗口策略

你可以把 EP 理解成：

它必须提前决定“我希望主机把我当成什么设备看待”。

2. 建立地址翻译窗口

EP 侧最关键的软件工作之一是地址映射配置。

因为 RC 和 EP 所看到的地址空间并不是天然一致的。

通常需要两类窗口：

  • inbound：RC 写到 BAR 窗口后，EP 内部把它翻译到本地寄存器或本地内存
  • outbound：EP 主动发起 DMA 时，把本地地址翻译成 RC 可见的系统地址

把它和前面的 BAR / DMA 对上，可以得到一个更清楚的对应关系：

软件动作 PCIe 方向 EP 侧关键窗口
RC 通过 BAR 访问 EP 寄存器 RC -> EP inbound
RC 通过 BAR 访问 EP 暴露的片上内存窗口 RC -> EP inbound
EP 主动向主机内存写结果 EP -> RC outbound
EP 主动从主机内存取输入数据 EP -> RC outbound

这一步如果没配好，会出现非常典型的问题：

  • RC 可以枚举到 EP，但读 BAR 数据全错
  • EP 发起 DMA 没报错，但主机内存没有正确变化
  • 访问地址“看起来对”，实际打到了错误窗口

3. EP 侧的软件初始化顺序

对一个 AI 加速卡来说，EP 软件通常要做：

  1. 初始化 PCIe 控制器工作模式为 EP
  2. 配置 BAR 对应的本地目标地址
  3. 配置 outbound DMA 窗口
  4. 初始化 doorbell、queue、mailbox 等共享结构
  5. 使能 MSI 或其他通知机制
  6. 等待主机侧 PCI 功能驱动完成配对初始化

这里的关键思想是：

EP 不是“被动等主机随便访问”，而是要先把一整套可访问的资源布局搭好。

八、RC 如何访问 EP：最先发生的一定是 PIO/MMIO

1. RC 访问 EP 的第一条通路是 BAR

在 Linux 驱动中，RC 访问 EP 最直接的方式是：

  • 先通过 BAR 拿到一段 MMIO 窗口
  • 再通过 readl/writel 访问寄存器

这些访问典型会用来做：

  • 读取设备版本号
  • 配置队列基地址
  • 写 doorbell
  • 查询状态寄存器
  • 触发某个控制命令

这类访问本质上是 PIO/MMIO，不适合大块数据传输，但它是所有后续交互的起点。

2. 典型初始化顺序

RC 侧驱动通常会这样做：

  1. 通过 BAR0 读设备 ID 和版本寄存器
  2. 配置共享内存或描述符队列地址
  3. 通知 EP “主机驱动已上线”
  4. 等待 EP 回写 ready 状态
  5. 再打开 DMA 和中断路径

所以从工程上看：

先靠 MMIO 建立控制通路，再靠 DMA 建立数据通路。

九、EP 如何访问 RC：核心是 DMA

EP 不能像 CPU 那样“直接看见主机所有内存”，它要想访问 RC 侧内存，必须通过 DMA。

1. DMA 的前提条件

至少需要这些条件同时满足：

  • 主机侧 PCI 功能驱动已经执行 pci_set_master()
  • RC 侧已经分配好 DMA buffer
  • RC 把 DMA buffer 的总线地址告诉了 EP
  • EP 侧 outbound 地址翻译窗口已经配置好

只有这样，EP 才能根据 RC 给出的 DMA 地址，向主机内存发起读写事务。

2. 一个典型的数据流

以“AI 加速卡向主机回传推理结果”为例：

  1. 主机侧 PCI 功能驱动分配一块 DMA buffer
  2. RC 把 DMA 地址通过 BAR 寄存器写给 EP
  3. EP 收到后，把本地结果搬到 outbound DMA 通路
  4. EP 发起 PCIe Memory Write TLP，把结果写入 RC 内存
  5. EP 通过 MSI 通知 RC：数据已完成
  6. RC 中断处理函数唤醒上层流程

这就是最典型的“控制走 BAR，数据走 DMA，完成靠 MSI”的工作模式。

十、MSI 在这个系统里为什么这么重要

1. 没有中断，系统只能傻等

如果没有中断，主机侧 PCI 功能驱动只能轮询设备状态寄存器。

这会带来几个问题：

  • CPU 浪费
  • 延迟更大
  • 并发处理更差

而 MSI/MSI-X 的好处是：

  • 本质上通过内存写触发中断
  • 不依赖传统共享引脚
  • 更适合多队列、多通道、高吞吐设备

2. 在 AI 加速卡场景下，MSI 常用于哪些事件

常见包括：

  • DMA 完成
  • 队列完成
  • 推理任务完成
  • 异常上报
  • doorbell 响应

主机侧 PCI 功能驱动收到 MSI 后，一般会：

  • 读取设备状态寄存器确认原因
  • 清中断
  • 回收描述符
  • 唤醒等待队列或上层框架

十一、把整个软件流程串起来看一遍

现在把整个过程串起来：

1. 上电到枚举

  • 主机和加速卡上电
  • RC 与 EP 完成链路训练
  • BIOS/UEFI 扫描 PCIe 拓扑
  • BIOS 给 EP 分配 BAR、Bus Number、桥窗口

2. Linux 接管

  • Linux 解析平台资源
  • PCI 子系统重新枚举
  • 创建设备对象
  • 绑定主机侧 PCI 功能驱动

3. 驱动初始化

  • 主机侧 PCI 功能驱动申请 BAR 资源并映射寄存器
  • 开启 Bus Master
  • 申请 MSI/MSI-X
  • 配置 DMA mask 和 DMA buffer

4. RC 与 EP 建立控制平面

  • RC 通过 BAR 向 EP 写配置
  • EP 建立 inbound/outbound 地址窗口
  • 双方协商 queue、doorbell、共享内存等结构

5. 建立数据平面

  • RC 把 DMA 地址交给 EP
  • EP 发起 DMA 访问 RC 内存
  • 传输结束后 EP 通过 MSI 告知 RC
  • RC 完成回收、唤醒和后续调度

这就是一条完整、可落地的 PCIe 软件实战主线。

十二、工程调试时最常见的故障点

最后给一个实战视角总结。PCIe 软件问题通常集中在下面几类：

1. 链路根本没起来

现象：

  • lspci 看不到设备
  • Root Port 下游为空

常见原因：

  • PERST# 时序不对
  • REFCLK 问题
  • lane 连接错误
  • PHY 初始化失败

2. 能枚举到，但 BAR 访问异常

现象：

  • Vendor ID 正常
  • 但驱动一访问寄存器就超时或读值异常

常见原因：

  • EP inbound window 没配好
  • BAR 映射目标地址错误
  • RC 侧访问了错误 BAR

3. MMIO 正常，但 DMA 不通

现象：

  • 设备寄存器能读写
  • 真正搬数据时没有结果

常见原因：

  • Bus Master 没开
  • DMA mask 配错
  • RC 提供给 EP 的 DMA 地址错误
  • EP outbound window 没配对

4. DMA 成功，但中断不来

现象：

  • 数据已经写入主机内存
  • 驱动却一直等不到完成通知

常见原因：

  • MSI 没申请成功
  • 设备侧 MSI 地址/数据配置不对
  • 中断处理函数没有正确清状态

十三、本文总结

从软件角度看，PCIe 不只是“总线”，而是一套完整的系统协作流程：

  • RC 负责发现和配置
  • EP 负责呈现能力和提供功能
  • BAR 负责控制面访问
  • DMA 负责数据面传输
  • MSI 负责事件通知

对于服务器 + AI 加速卡这种场景，真正重要的不是记住某个寄存器名字，而是建立下面这个整体认知：

先有链路，再有枚举；先有地址窗口，再有寄存器访问；先有控制平面，再有 DMA 数据平面。

理解了这一条主线，后面再看：

  • Root Port 驱动
  • Endpoint 控制器驱动
  • BAR 映射
  • inbound/outbound ATU
  • MSI/MSI-X
  • DMA 描述符

就不会再是零散知识点，而会变成一个完整的工程系统。
